## Що ви зможете зробити

Після цього модуля ви зможете:

- **Розв'язувати** DNS-імена сервісів і Подів між просторами імен, використовуючи короткі імена, повні кваліфіковані імена, пошукові домени та SRV-записи.
- **Діагностувати** збої DNS, порівнюючи симптоми застосунку, файл `/etc/resolv.conf` Пода, стан CoreDNS, логи CoreDNS та endpoints Сервісу.
- **Налаштовувати** CoreDNS безпечно для записів hosts, переспрямування на вищі резолвери (upstream), поведінки кешу та відкату.
- **Оцінювати** політики DNS `ClusterFirst`, `Default`, `ClusterFirstWithHostNet` і `None` під час проєктування Подів.

## Чому цей модуль важливий

Гіпотетичний сценарій: ваша команда розгортає новий API за Сервісом Kubernetes, проби готовності (readiness) зелені, у Сервісу є endpoints, але фронтенд усе одно повідомляє `could not resolve host`. Команда застосунку просить змінити правила фаєрвола, бо симптом схожий на проблему зі зв'язністю, тоді як платформова команда бачить справні Поди й справні Сервіси. Найшвидший вихід із цієї плутанини — розділити три питання: чи ім'я взагалі розв'язалося, чи розв'язалося воно в очікувану адресу, і чи можуть пакети дістатися endpoint після успішного розв'язання?

DNS у Kubernetes — це рівень іменування, який дозволяє робочим навантаженням використовувати стабільні імена Сервісів замість того, щоб ганятися за IP-адресами Подів, які змінюються щоразу, коли Поди замінюються. Кожен запит до імені на кшталт `web-svc`, `web-svc.default` або `web-svc.default.svc.cluster.local` залежить від налаштувань резолвера, які впроваджує kubelet, від Сервісу ClusterIP з іменем `kube-dns` та від Подів CoreDNS, які відповідають на DNS-запити з урахуванням специфіки Kubernetes. Коли цей рівень виходить з ладу, багато не пов'язаних між собою застосунків можуть здатися несправними одночасно, бо їхнє перше звертання до залежності взагалі не доходить до мережевого шляху, який ви збиралися перевірити.

Цей модуль трактує DNS як операційну систему, а не як магічну таблицю пошуку. Ви простежите, як Под отримує налаштування DNS, як CoreDNS перетворює об'єкти Сервісів і Подів на записи, чому пошукові домени роблять короткі імена зручними, але подеколи несподіваними, і як CoreDNS переспрямовує зовнішні запити на вищі резолвери. Ви також відпрацюєте характерну для CKA звичку діагностики — спочатку довести, де саме розташований збій, перш ніж змінювати конфігурацію DNS на рівні всього кластера.

Аналогія з телефонним довідником досі корисна, якщо пам'ятати про її межі. DNS — це телефонний довідник кластера, CoreDNS — оператор, який відповідає на дзвінки-пошуки, а Сервіс `kube-dns` — це стабільний номер телефону, який набирають Поди. На відміну від друкованого довідника, цей перебудовується безперервно з API Kubernetes, кешується на короткі проміжки часу і залежить від політики резолвера кожного окремого Пода.

## Архітектура DNS у Kubernetes

DNS у Kubernetes починається ще до того, як запуститься будь-який код застосунку. Коли kubelet створює пісочницю (sandbox) Пода, він записує конфігурацію резолвера всередину Пода, щоб звичайні бібліотеки могли звертатися до DNS, нічого не знаючи про Kubernetes. За політикою `ClusterFirst` за замовчуванням ця конфігурація резолвера вказує на Сервіс DNS кластера і містить пошукові домени, які розгортають короткі імена Сервісів у повні імена Kubernetes. Застосунок усе одно викликає `getaddrinfo`, `curl` чи резолвер мовного середовища виконання, але пошук імені спрямовується в DNS-шлях кластера.

```text
┌────────────────────────────────────────────────────────────────┐
│                   Kubernetes DNS Architecture                   │
│                                                                 │
│   ┌────────────────┐                                           │
│   │     Pod        │                                           │
│   │                │                                           │
│   │ curl web-svc   │                                           │
│   │      │         │                                           │
│   │      ▼         │                                           │
│   │ /etc/resolv.conf                                           │
│   │ nameserver 10.96.0.10  ──────────────────────┐            │
│   │ search default.svc...                         │            │
│   └────────────────┘                              │            │
│                                                   │            │
│                                                   ▼            │
│   ┌──────────────────────────────────────────────────────────┐│
│   │              CoreDNS Service (10.96.0.10)                ││
│   │                                                           ││
│   │  ┌─────────┐ ┌─────────┐                                 ││
│   │  │CoreDNS  │ │CoreDNS  │  (commonly 2 replicas)          ││
│   │  │  Pod    │ │  Pod    │                                 ││
│   │  └────┬────┘ └────┬────┘                                 ││
│   │       │           │                                       ││
│   │       └─────┬─────┘                                       ││
│   │             ▼                                             ││
│   │    Query: web-svc.default.svc.cluster.local              ││
│   │             │                                             ││
│   │             ▼                                             ││
│   │    Response: 10.96.45.123 (Service ClusterIP)            ││
│   └──────────────────────────────────────────────────────────┘│
│                                                                 │
└────────────────────────────────────────────────────────────────┘
```

CoreDNS зазвичай розгортається як Deployment у просторі імен `kube-system`, перед яким стоїть Сервіс з іменем `kube-dns` для сумісності зі старішим додатком kube-dns. Ця назва-сумісник важлива під час діагностики, бо запущені Поди — це CoreDNS, але Сервіс, яким користуються клієнти, часто все ще називається `kube-dns`. Сервіс надає стабільний ClusterIP, і kubelet записує цю IP-адресу як `nameserver` для Подів, які використовують DNS кластера.

| Компонент | Розташування | Призначення |
|-----------|----------|---------|
| CoreDNS Deployment | простір імен `kube-system` | Запускає Поди CoreDNS, які відповідають на DNS-запити |
| CoreDNS Service | простір імен `kube-system` | Надає стабільний ClusterIP для DNS-запитів, зазвичай з іменем `kube-dns` |
| ConfigMap із Corefile | простір імен `kube-system` | Зберігає конфігурацію плагінів CoreDNS |
| `/etc/resolv.conf` Пода | Кожен Под | Спрямовує бібліотеки резолвера до CoreDNS і визначає поведінку пошуку |

Важлива операційна деталь полягає в тому, що DNS-пошуки — це звичайні запити UDP або TCP до IP-адреси Сервісу CoreDNS, але на імена Kubernetes CoreDNS відповідає, спостерігаючи за API Kubernetes. Якщо Поди CoreDNS не працюють, Сервіс не має корисних бекендів. Якщо Поди працюють, але не можуть зв'язатися з API-сервером, імена Kubernetes можуть не розв'язуватися, тоді як зовнішнє переспрямування може виглядати нормально. Якщо kubelet записує несподіваний `resolv.conf`, в одного окремого Пода може зламатися DNS, навіть коли система DNS кластера справна для всіх інших.

```bash
# Inside any Pod
cat /etc/resolv.conf

# Typical output:
nameserver 10.96.0.10
search default.svc.cluster.local svc.cluster.local cluster.local
options ndots:5
```

| Поле | Призначення |
|-------|---------|
| `nameserver` | IP-адреса Сервісу CoreDNS |
| `search` | Домени, які резолвер додає, коли процес використовує коротке або відносне ім'я |
| `ndots:5` | Імена з менш ніж п'ятьма крапками трактуються спершу як відносні, тож пошукові домени пробуються перед остаточним абсолютним запитом |

Налаштування `ndots:5` дивує людей, бо ім'я на кшталт `api.example.com` має крапки, але для багатьох резолверів їх недостатньо, щоб спершу спробувати його як абсолютне. Резолвер може спершу запитати `api.example.com.default.svc.cluster.local`, потім `api.example.com.svc.cluster.local`, потім `api.example.com.cluster.local` і лише після цього спробувати власне `api.example.com`. Така поведінка покращує ергономіку коротких імен усередині кластера, але може додавати затримку для зовнішніх імен, якщо застосунок виконує багато нових DNS-пошуків.

Зупиніться й передбачте: якщо Под може розв'язати `kubernetes.default.svc.cluster.local`, але не може розв'язати `example.com`, яка частина DNS-шляху вже доведено справна, а яка частина ще потребує дослідження? Шлях плагіна Kubernetes працює принаймні для одного внутрішньокластерного Сервісу, тож ваші наступні перевірки мають рухатися в бік плагіна `forward`, доступності вищого резолвера, правил мережевої політики чи фаєрвола від CoreDNS до вищого DNS і будь-яких записів у логах CoreDNS про зовнішні запити.

Для діагностики на CKA починайте з поваги до рівнів. Невдалий HTTP-запит за іменем може бути збоєм DNS, збоєм селектора Сервісу, збоєм готовності endpoint, відмовою NetworkPolicy, невідповідністю порту застосунку або тайм-аутом після розв'язання. Діагностика DNS потужна тим, що може швидко зняти підозру з першого рівня, але вона не доводить, що весь шлях до сервісу справний.

```bash
# Check the DNS Service and the CoreDNS Pods that back it.
kubectl get svc kube-dns -n kube-system
kubectl get endpoints kube-dns -n kube-system
kubectl get pods -n kube-system -l k8s-app=kube-dns -o wide
```

Якщо у Сервісу немає endpoints, не марнуйте час на зміни YAML застосунку. Резолвер Пода може скільки завгодно вказувати на правильний ClusterIP, але Сервісу без endpoints просто нема куди корисно надіслати DNS-пакет. Якщо endpoints існують і Поди CoreDNS готові, наступне змістовне питання — чи розуміє CoreDNS ім'я, яке ви запитали, і чи запитує клієнтський Под саме те ім'я, яке ви думаєте.

CoreDNS також перебуває на межі довіри, яку легко проґавити. Команди застосунків рідко мають дозвіл редагувати простір імен `kube-system`, але кожен застосунок залежить від результатів, які там продукуються. Це означає, що інциденти з DNS часто потребують координації між власниками робочих навантажень, операторами кластера, а іноді й мережевими адміністраторами, які керують вищими резолверами. Хороші докази скорочують цю координацію: покажіть точне ім'я, простір імен клієнта, файл резолвера, тип DNS-відповіді та чи розв'язується відоме ім'я кластера.

Спостереження за API, яке стоїть за CoreDNS, — ще одна причина відокремлювати стан об'єкта від стану DNS. Об'єкт Сервісу може існувати, тоді як його селектор не збігається з жодним Подом, і CoreDNS усе одно може повертати ClusterIP Сервісу, бо DNS-записи ClusterIP прив'язані до Сервісу, а не до готовності endpoint. Headless-Сервіс поводиться інакше, бо його DNS-відповіді залежать безпосередньо від адрес endpoints. Коли ви знаєте, який тип Сервісу тестуєте, DNS-відповідь стає підказкою, а не заплутаною несподіванкою.

Пам'ятайте, що IP-адреса Сервісу `kube-dns` не особлива тим, що вона завжди `10.96.0.10`; ця адреса лише поширене значення за замовчуванням у багатьох кластерах. Стабільний факт полягає в тому, що kubelet записує IP-адресу Сервісу DNS кластера в конфігурацію резолвера Пода відповідно до налаштувань DNS кластера та політики DNS самого Пода. У реальних середовищах завжди читайте Сервіс і файл резолвера Пода, перш ніж приймати числову адресу з туторіалу чи іншого кластера як істину.

## Імена сервісів, пошукові домени та записи

DNS-імена Сервісів Kubernetes мають передбачувану ієрархію: ім'я Сервісу, простір імен, фіксована мітка `svc` і домен кластера. Домен кластера за замовчуванням — `cluster.local`, але кластери можна налаштувати інакше, тож звички діагностики мають фокусуватися на читанні фактичного списку пошуку Пода, а не на запам'ятовуванні одного домену як універсального. У більшості навчальних кластерів `web-svc.production.svc.cluster.local` означає Сервіс з іменем `web-svc` у просторі імен `production`.

```text
┌────────────────────────────────────────────────────────────────┐
│                   Service DNS Naming                            │
│                                                                 │
│   Full format (FQDN):                                          │
│   <service>.<namespace>.svc.<cluster-domain>                   │
│                                                                 │
│   Example: web-svc.production.svc.cluster.local                │
│            ───────  ──────────  ───  ─────────────             │
│               │        │         │        │                    │
│           service  namespace   fixed   cluster domain          │
│                                 suffix  (default)              │
│                                                                 │
└────────────────────────────────────────────────────────────────┘
```

Найкоротше робоче ім'я залежить від простору імен клієнтського Пода та його пошукових доменів. З Пода в `default` ім'я `web-svc` розгортається спершу в `web-svc.default.svc.cluster.local`, тож воно дістається простору імен `default`, якщо такий Сервіс існує. Щоб дістатися Сервісу в іншому просторі імен, використовуйте `api.production` або повне ім'я `api.production.svc.cluster.local`. Короткі імена зручні для трафіку в межах того самого простору імен, але явні імена безпечніші у спільних бібліотеках, значеннях Helm та інтеграціях між просторами імен.

```bash
# From a Pod in the "default" namespace, reaching "web-svc" in "default":
curl web-svc
curl web-svc.default
curl web-svc.default.svc
curl web-svc.default.svc.cluster.local

# From a Pod in "default", reaching "api" in "production":
curl api
curl api.production
curl api.production.svc.cluster.local
```

Перша команда для іншого простору імен вище навмисно підступна: `curl api` не означає «знайди API, де б воно не було». Це означає «спробуй це відносне ім'я через мій список пошуку», тож `api.default.svc.cluster.local` пробується раніше за будь-що інше. Якщо локальний Сервіс `api` існує, запит дістається саме цього локального Сервісу. Якщо ж його немає, резолвер продовжує пробувати пошукові суфікси і зрештою може запитати зовнішній резолвер про `api`, що все одно не те саме, що `api.production`.

```text
┌────────────────────────────────────────────────────────────────┐
│                   Search Domain Resolution                      │
│                                                                 │
│   Pod in namespace "default" resolves "web-svc":               │
│                                                                 │
│   search default.svc.cluster.local svc.cluster.local ...       │
│                                                                 │
│   Step 1: Try web-svc.default.svc.cluster.local                │
│           └── Found! Returns IP                                │
│                                                                 │
│   If not found:                                                │
│   Step 2: Try web-svc.svc.cluster.local                        │
│   Step 3: Try web-svc.cluster.local                            │
│   Step 4: Try web-svc (external DNS)                           │
│                                                                 │
└────────────────────────────────────────────────────────────────┘
```

Зупиніться й передбачте: Под у просторі імен `staging` виконує `curl api-service`, а в кластері є `api-service` і в `staging`, і в `production`. Який із них дістане Под і чому? Под дістається `api-service.staging.svc.cluster.local`, бо першим пробується пошуковий домен його власного простору імен. Це корисна ізоляція, коли команди володіють своїми просторами імен, але вона стає ризиком, коли конфігурація застосунку покладається на неоднозначні імена Сервісів.

DNS-записи Подів також існують, хоча Сервіси мають залишатися звичайною стабільною ціллю для більшості застосунків. IP Пода на кшталт `10.244.1.5` можна подати як `10-244-1-5.default.pod.cluster.local`, а Поди StatefulSet отримують передбачувані DNS-ідентичності у парі з headless-Сервісом. Ці форми корисні для систем, яким потрібні стабільні ідентичності вузлів-учасників, але вони також прив'язують клієнтів до окремих Подів тісніше, ніж це робить Сервіс ClusterIP.

```text
┌────────────────────────────────────────────────────────────────┐
│                   Pod DNS Names                                 │
│                                                                 │
│   Pod IP: 10.244.1.5                                           │
│   DNS: 10-244-1-5.default.pod.cluster.local                    │
│        ──────────  ───────  ───  ─────────────                 │
│          IP with   namespace pod  cluster domain               │
│          dashes                                                 │
│                                                                 │
│   For StatefulSet Pods with headless Service:                  │
│   DNS: web-0.web-svc.default.svc.cluster.local                 │
│        ─────  ───────  ───────  ───                            │
│        pod    headless  namespace                              │
│        name   service                                          │
│                                                                 │
└────────────────────────────────────────────────────────────────┘
```

Headless-Сервіси заслуговують на особливу увагу, бо вони навмисно прибирають єдину абстракцію ClusterIP. Коли встановлено `clusterIP: None`, DNS може повертати IP-адреси Подів, що стоять за Сервісом, замість віртуального IP Сервісу, що корисно для виявлення вузлів-учасників і робочих навантажень StatefulSet. Компроміс у тому, що клієнти тепер бачать більше топології робочого навантаження, тож мають обробляти кілька повернутих адрес, плинність endpoints та поведінку з'єднань, яку звичайний Сервіс ClusterIP зазвичай приховує.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-svc
spec:
  clusterIP: None
  selector:
    app: web
  ports:
  - name: http
    port: 80
    targetPort: 8080
```

SRV-записи додають до DNS-відповіді інформацію про порт, що корисно, коли клієнти виявляють і ім'я, і іменований порт. Kubernetes створює SRV-записи для іменованих портів Сервісу у формі `_<port-name>._<protocol>.<service>.<namespace>.svc.<cluster-domain>`. Іменований порт має значення, бо неіменований порт не дає DNS стабільної символьної мітки порту для публікації в SRV-записі.

```bash
# Query an SRV record for a named Service port.
# From a netshoot (or other dig-equipped) pod:
dig SRV _http._tcp.web-svc.default.svc.cluster.local

# Typical answer shape:
# _http._tcp.web-svc.default.svc.cluster.local. 30 IN SRV 0 100 80 web-svc.default.svc.cluster.local.
```

| Форма імені | Приклад | Найкраще застосування | Операційний ризик |
|-----------|---------|----------|------------------|
| Коротке ім'я Сервісу | `web-svc` | Виклики в межах того самого простору імен, де імена однозначні | Може розв'язатися в неправильний локальний Сервіс простору імен |
| Сервіс плюс простір імен | `web-svc.default` | Виклики між просторами імен у конфігурації застосунку | Залежить від пошукового суфікса `svc.cluster.local` |
| Повний FQDN Сервісу | `web-svc.default.svc.cluster.local` | Діагностика, спільна конфігурація та явні залежності | Багатослівніший і прив'язаний до домену кластера |
| Ім'я headless-Сервісу | `web-svc.default.svc.cluster.local` | Виявлення стабільних вузлів-учасників і прямі відповіді endpoints | Клієнти мають терпіти кілька змінних IP |
| SRV-запис | `_http._tcp.web-svc.default.svc.cluster.local` | Виявлення іменованого порту й цілі разом | Працює лише тоді, коли порти Сервісу іменовані |

Перш ніж це запускати, який результат ви очікуєте від headless-Сервісу з трьома готовими Подами: один IP, кілька IP чи жодного IP? Правильне очікування — кілька IP-адрес endpoints, коли селектор збігається з готовими Подами, а DNS-запит звертається до імені Сервісу. Якщо ви не бачите відповіді, перевірте селектор Сервісу та endpoints, перш ніж звинувачувати CoreDNS.

Пошукові домени — це зручні можливості, але водночас і форма прихованого контексту. Той самий образ контейнера застосунку може розв'язувати те саме голе ім'я по-різному, коли запускається у двох просторах імен, навіть якщо команда всередині контейнера ідентична. Саме тому виробнича конфігурація має робити межі власності явними. Усталене значення бібліотеки `db` може здаватися безневинним у просторі імен розробки, а потім стати небезпечним у кластері, де кожна команда володіє локальним Сервісом `db`.

Повні кваліфіковані імена не завжди необхідні, але вони чудові діагностичні інструменти. Коли коротке ім'я не спрацьовує, запитайте повний FQDN Сервісу й порівняйте результат. Якщо повне ім'я працює, а коротке ні, Сервіс, імовірно, існує і CoreDNS, імовірно, його знає, тож баг — у поведінці пошуку або в конфігурації клієнта. Якщо обидві форми не спрацьовують, рухайтеся в бік існування Сервісу, написання простору імен, стану CoreDNS чи налаштувань резолвера клієнта.

Домен кластера — ще одне місце, де припущення можуть просочитися в маніфести. Багато прикладів використовують `cluster.local`, і більшість навчальних кластерів теж, але Kubernetes дозволяє інший домен кластера. Конфігурація застосунку, яка жорстко закодовує повне ім'я з `cluster.local`, є явною, але водночас менш переносною, ніж `service.namespace`, коли списку пошуку можна довіряти. Під час іспитів та реагування на інциденти використовуйте повний FQDN, щоб усунути неоднозначність; під час проєктування продукту вирішуйте, що важливіше — переносність чи явність.

## Конфігурація та налаштування CoreDNS

CoreDNS налаштовується через ConfigMap з іменем `coredns` у `kube-system`. Corefile усередині цього ConfigMap визначає ланцюжок плагінів, і кожен плагін або обробляє, або змінює, спостерігає, кешує чи переспрямовує запит. Саме ця модель плагінів — причина, чому CoreDNS замінив старіший додаток kube-dns в операціях епохи Kubernetes: він компактний, розширюваний і легкий для розуміння, коли ви читаєте Corefile згори донизу.

```bash
# Check CoreDNS pods.
kubectl get pods -n kube-system -l k8s-app=kube-dns

# Check the CoreDNS Deployment.
kubectl get deployment coredns -n kube-system

# Check the DNS Service. The Service is commonly named "kube-dns" for compatibility.
kubectl get svc kube-dns -n kube-system

# View CoreDNS configuration.
kubectl get configmap coredns -n kube-system -o yaml
```

Усталений Corefile відрізняється залежно від дистрибутива, але кластер Kubernetes зазвичай містить ті самі концептуальні частини: ендпоінти стану для проб, перевірки готовності, плагін `kubernetes` для записів Сервісів і Подів, метрики Prometheus, переспрямування на вищі резолвери, кешування, виявлення циклів, автоматичне перезавантаження та балансування навантаження. Синтаксична помилка або погано розташований плагін можуть вплинути на кожен Под у кластері, тож трактуйте зміни CoreDNS як зміни інфраструктури, а не як редагування ConfigMap одного застосунку.

```yaml
# CoreDNS ConfigMap
apiVersion: v1
kind: ConfigMap
metadata:
  name: coredns
  namespace: kube-system
data:
  Corefile: |
    .:53 {
        errors
        health {
            lameduck 5s
        }
        ready
        kubernetes cluster.local in-addr.arpa ip6.arpa {
            pods insecure
            fallthrough in-addr.arpa ip6.arpa
            ttl 30
        }
        prometheus :9153
        forward . /etc/resolv.conf {
            max_concurrent 1000
        }
        cache 30
        loop
        reload
        loadbalance
    }
```

| Плагін | Призначення | Підказка для діагностики |
|--------|---------|----------------------|
| `kubernetes` | Розв'язує імена Сервісів і Подів Kubernetes | Імена кластера не спрацьовують, коли доступ до API, домен кластера чи налаштування плагіна неправильні |
| `forward` | Надсилає нерозв'язані запити вищим DNS | Зовнішні імена не спрацьовують, коли вищі резолвери або шляхи виходу зламані |
| `cache` | Кешує відповіді, щоб зменшити навантаження | Відповіді, що здаються застарілими, можуть слідувати за короткими вікнами TTL |
| `errors` | Логує помилки DNS | Логи CoreDNS стають кориснішими під час збоїв |
| `health` | Надає ендпоінт перевірки стану | Поведінка liveness залежить від доступності цього ендпоінта |
| `ready` | Надає ендпоінт готовності | Поди не мають отримувати трафік, доки плагіни не готові |
| `prometheus` | Експонує метрики | Частоту запитів, помилки та затримку можна збирати для спостережуваності |
| `loop` | Виявляє цикли переспрямування | Повторне самопереспрямування може аварійно завершити або вимкнути CoreDNS |
| `reload` | Перезавантажує змінений вміст Corefile | У багатьох конфігураціях зміни ConfigMap можуть застосуватися без ручної заміни Подів |
| `loadbalance` | Рандомізує порядок DNS-відповідей | Клієнти уникають постійного вибору першої повернутої адреси |

Плагін `kubernetes` — це та частина, що змушує об'єкт Сервісу з'явитися як DNS-відповідь. Він спостерігає за ресурсами Kubernetes і відповідає за налаштовані зони, зазвичай `cluster.local`, `in-addr.arpa` та `ip6.arpa`. Рядок `fallthrough` усередині цього плагіна каже CoreDNS передавати промахи зворотного пошуку наступним плагінам замість того, щоб зупинятися одразу, що відрізняється від успішного пошуку Сервісу, де плагін відповідає напряму.

Власні записи інколи потрібні для застарілих систем, імен зі split-horizon чи лабораторних середовищ. Найбезпечніший патерн — додати вузький запис `hosts` або конкретне правило переспрямування, зберігаючи при цьому звичайне розв'язання Kubernetes. Небезпечний патерн — вставити плагін, який повертає `NXDOMAIN` для кожного імені, якого не знає, бо тоді решта ланцюжка плагінів так і не отримає шансу відповісти на імена Сервісів кластера.

```yaml
# Add custom DNS entries.
apiVersion: v1
kind: ConfigMap
metadata:
  name: coredns
  namespace: kube-system
data:
  Corefile: |
    .:53 {
        errors
        health {
            lameduck 5s
        }
        ready
        kubernetes cluster.local in-addr.arpa ip6.arpa {
            pods insecure
            fallthrough in-addr.arpa ip6.arpa
            ttl 30
        }
        hosts {
            10.0.0.1 custom.example.com
            fallthrough
        }
        forward example.com 10.0.0.53
        prometheus :9153
        forward . /etc/resolv.conf
        cache 30
        loop
        reload
        loadbalance
    }
```

`fallthrough` усередині блоку `hosts` не є декоративним. Без нього запит, який не збігається з `custom.example.com`, може зупинитися на плагіні `hosts` і повернути негативну відповідь замість того, щоб продовжити до плагіна Kubernetes чи загального форвардера. Цей один пропущений рядок може перетворити невелике власне зіставлення на загальнокластерний збій виявлення Сервісів, тому редагування CoreDNS варто рецензувати й розгортати з готовою під рукою швидкою командою відкату.

```bash
# After editing, restart CoreDNS if your environment does not rely solely on reload.
kubectl rollout restart deployment coredns -n kube-system

# Watch replacement Pods become ready before declaring the change complete.
kubectl rollout status deployment coredns -n kube-system
```

Сценарій вправи: вам потрібно, щоб `legacy-api.internal` розв'язувалося в `10.0.5.100` для кожного Пода, тоді як звичайні імена Сервісів продовжують працювати. Блок `hosts` може розв'язати цю вимогу, але загальнокластерний радіус ураження означає, що ви маєте зберегти попередній ConfigMap, змінити лише мінімум рядків Corefile, перевірити `kubernetes.default.svc.cluster.local`, перевірити нове застаріле ім'я та переглянути логи CoreDNS. Якщо будь-яка з перевірок не вдасться, відкотіть ConfigMap, перш ніж розбиратися з командами застосунків поодинці.

```bash
# Capture the current Corefile before editing.
kubectl get configmap coredns -n kube-system -o yaml > coredns-before.yaml

# Open the live ConfigMap in your editor.
kubectl edit configmap coredns -n kube-system
```

Не використовуйте налаштування CoreDNS, щоб приховати погане іменування Сервісів. Якщо команда раз за разом плутає `db` у кількох просторах імен, додавання глобального DNS-аліаса може зробити наступний збій складнішим для діагностики, бо ім'я більше не відображає власності чи простору імен. Надавайте перевагу явній конфігурації застосунку, стабільним правилам іменування та посиланням на Сервіси з кваліфікацією простору імен, перш ніж тягтися до загальнокластерних перезаписів DNS.

Трактуйте Corefile як виконуваний інфраструктурний код. Невелика помилка відступу може не мати значення для YAML, якщо блоковий скаляр усе одно парситься, але хибно сформований Corefile може завадити CoreDNS коректно обслуговувати запити після перезавантаження. Перед редагуванням захопіть поточний ConfigMap, зробіть одну концептуальну зміну і перевірте як відоме ім'я кластера, так і потрібну вам власну поведінку. Якщо у вашому середовищі є контроль змін, включіть до запису про зміну точну команду відкату.

Кешування — ще одна причина, чому зміни DNS можуть деякий час здаватися неузгодженими. CoreDNS може кешувати відповіді згідно з налаштуваннями плагіна `cache`, а клієнтські бібліотеки чи середовища виконання мов можуть підтримувати власні кеші. Якщо ви змінюєте Сервіс, CoreDNS чи вищий запис, а один процес ще короткий час бачить стару відповідь, перевірте TTL і поведінку клієнта, перш ніж припускати, що кластер проігнорував вашу зміну. Для критичних міграцій проєктуйте перехідний період, а не покладайтеся на миттєву збіжність DNS.

Правила переспрямування заслуговують на таку саму вузькість, як і правила фаєрвола. Широке `forward .` надсилає все, що не оброблено раніше, вищим резолверам, тоді як специфічне для домену переспрямування на кшталт `forward example.com 10.0.0.53` впливає лише на обраний суфікс. Коли приватна корпоративна зона має розв'язуватися всередині Подів, вузьке правило в стилі stub зазвичай легше осягнути, ніж заміна кожного вищого резолвера. Воно також робить ізоляцію збоїв чіткішою, коли не спрацьовує лише один зовнішній суфікс.

Спостережуваність перетворює CoreDNS із чорної скриньки на сервіс, який можна діагностувати. Логи допомагають під час гострих збоїв, але метрики кращі для виявлення зростання обсягу запитів, частоти помилок і затримки до того, як користувачі поскаржаться. Оскільки кожен Под залежить від DNS, насичення CoreDNS може виглядати як випадкове сповільнення застосунків у багатьох просторах імен. У продакшені оповіщення про доступність CoreDNS і патерни помилок — практична частина надійності виявлення сервісів, а не необов'язковий додаток.

## Діагностика збоїв DNS

Діагностику DNS варто починати з реального клієнтського Пода або з тимчасового Пода в тому самому просторі імен. Тестування на вашому ноутбуці майже нічого не доводить про пошукові домени кластера, політики DNS, NetworkPolicy чи IP Сервісу CoreDNS, що його впроваджує kubelet. Тимчасовий Под BusyBox чи netshoot дає вам ту саму поведінку резолвера, яку отримує застосунок, і це робить ваші докази значно кориснішими під час інциденту чи завдання на іспиті.

```text
DNS Issue?
    │
    ├── Step 1: Test from inside a Pod
    │   kubectl run test --rm -it --image=busybox:1.36 --restart=Never -- nslookup <service>
    │       │
    │       ├── Works? -> DNS is fine, issue is elsewhere
    │       │
    │       └── Fails? -> Continue debugging
    │
    ├── Step 2: Check CoreDNS is running
    │   kubectl get pods -n kube-system -l k8s-app=kube-dns
    │       │
    │       └── Not running? -> Fix CoreDNS Deployment
    │
    ├── Step 3: Check CoreDNS logs
    │   kubectl logs -n kube-system -l k8s-app=kube-dns
    │       │
    │       └── Errors? -> Check Corefile config
    │
    ├── Step 4: Check Pod resolv.conf
    │   kubectl exec <pod-name> -- cat /etc/resolv.conf
    │       │
    │       └── Wrong nameserver? -> Check kubelet and Pod DNS policy
    │
    └── Step 5: Test external DNS
        kubectl run test --rm -it --image=busybox:1.36 --restart=Never -- nslookup example.com
            │
            └── Fails? -> Check forward config and upstream reachability
```

Цей робочий процес розділяє симптоми, які звучать схоже. `NXDOMAIN` зазвичай означає, що DNS-сервер відповів, що імені не існує, що вказує на написання, простір імен, існування Сервісу чи поведінку пошуку. Тайм-аут зазвичай означає, що запит не отримав відповіді, що вказує на доступність CoreDNS, NetworkPolicy, проблеми CNI чи збій вищого DNS. `SERVFAIL` повідомляє, що DNS-сервер відповів, але не зміг завершити пошук, що часто скеровує вас до логів CoreDNS чи стану вищого резолвера.

```bash
# Test DNS from inside the cluster.
kubectl run dns-test --rm -it --image=busybox:1.36 --restart=Never -- \
  nslookup kubernetes

# Test a specific Service FQDN.
kubectl run dns-test --rm -it --image=busybox:1.36 --restart=Never -- \
  nslookup web-svc.default.svc.cluster.local

# Test with the DNS Service IP explicitly.
kubectl run dns-test --rm -it --image=busybox:1.36 --restart=Never -- \
  nslookup web-svc "$(kubectl get svc kube-dns -n kube-system -o jsonpath='{.spec.clusterIP}')"
```

Ці три тести відповідають на різні питання. Перший питає, чи може усталений шлях резолвера в тимчасовому Поді розв'язати відомий Сервіс кластера. Другий усуває неоднозначність простору імен, використовуючи повне ім'я Сервісу. Третій оминає налаштування `nameserver` Пода і надсилає запит на поточний IP Сервісу DNS, що допомагає визначити, чи неправильний `/etc/resolv.conf`, чи сам CoreDNS відповідає некоректно.

```bash
# Check resolver configuration in an existing Pod.
kubectl exec my-app-pod -- cat /etc/resolv.conf

# Check CoreDNS logs.
kubectl logs -n kube-system -l k8s-app=kube-dns --tail=50

# Verify CoreDNS is responding for the Kubernetes Service.
kubectl run dns-test --rm -it --image=busybox:1.36 --restart=Never -- \
  nslookup kubernetes.default.svc.cluster.local
```

Використовуйте багатший образ для діагностики, коли вам потрібні `dig`, `host`, інструменти для пакетів чи повторні інтерактивні тести. BusyBox швидкий і його достатньо для багатьох завдань іспиту, але netshoot дає більше деталей про DNS і загальні мережеві інструменти. Компроміс — доступність образу: у обмежених середовищах малий образ, який уже закешований, може бути надійнішим за насичений інструментами образ, який потрібно завантажувати під час збою.

```bash
# Create a debug Pod with more networking tools.
kubectl run dns-debug --image=nicolaka/netshoot --restart=Never -- sleep 3600

# Wait for the Pod to be ready.
kubectl wait --for=condition=ready pod/dns-debug --timeout=60s

# Use it for DNS debugging.
kubectl exec -it dns-debug -- dig web-svc.default.svc.cluster.local
kubectl exec -it dns-debug -- host web-svc
kubectl exec -it dns-debug -- nslookup web-svc

# Cleanup.
kubectl delete pod dns-debug
```

Коли DNS працює, продовжуйте, доки не доведете наступний рівень. Успішний `nslookup web-svc.default.svc.cluster.local` доводить лише розв'язання імені. Він не доводить, що Сервіс обирає готові endpoints, що цільовий порт правильний, що NetworkPolicy дозволяє трафік чи що застосунок слухає. Після DNS застосовуйте `kubectl get endpointslices`, `kubectl describe service` і справжній тест з'єднання, коли заявлений симптом — тайм-аут застосунку.

| Симптом | Імовірна причина | Як підтвердити | Кращий наступний крок |
|---------|--------------|----------------|------------------|
| `NXDOMAIN` | Невідповідність імені Сервісу, простору імен чи шляху пошуку | Запитайте повний FQDN і перелічіть Сервіси у просторі імен | Виправте ім'я або використайте конфігурацію з кваліфікацією простору імен |
| Тайм-аут | На DNS-пакет немає відповіді | Запитайте IP Сервісу CoreDNS напряму й перевірте мережеву політику | Перевірте доступність CoreDNS, CNI та правила політики |
| `SERVFAIL` | CoreDNS чи вищий резолвер не може завершити запит | Перевірте логи CoreDNS і запитайте відоме ім'я кластера | Відокремте збої плагіна Kubernetes від збоїв переспрямування |
| Повернуто неправильний IP | Несподіваний Сервіс, застарілий кеш клієнта чи поведінка headless-endpoint | Порівняйте DNS-відповідь з ClusterIP Сервісу та EndpointSlices | Виправте селектори чи дочекайтеся спливання TTL/кешу клієнта |
| Зовнішні домени не спрацьовують | Шлях переспрямування чи вищий DNS зламані | Розв'яжіть імена Сервісів кластера, а потім протестуйте зовнішні імена | Перевірте `forward` у Corefile, DNS вузла та правила виходу |

Зупиніться й подумайте: Под повідомляє `connection timed out`, викликаючи інший Сервіс за іменем. Чи це обов'язково проблема DNS? Ні. Спершу розв'яжіть ім'я з того самого простору імен, потім з'єднайтеся з розв'язаною ціллю чи іменем Сервісу на очікуваному порту, а потім перевірте endpoints Сервісу. DNS — лише один рівень, і зміна CoreDNS до доведення збою пошуку імені може створити ширший інцидент, ніж той, з якого ви почали.

Зручна для іспиту звичка — записувати найменший факт, який доводить кожна команда. `kubectl get pods -n kube-system -l k8s-app=kube-dns` доводить, що Поди існують, а не що вони коректно відповідають. `kubectl logs` доводить, чи бачив або повідомляв CoreDNS помилки, а не що кожен клієнт може його дістатися. `cat /etc/resolv.conf` доводить налаштований шлях резолвера клієнта, а не те, що резолвер справний. Така дисципліна запобігає безладному перестрибуванню між командами під тиском часу.

Розташування простору імен має значення навіть для тимчасових Подів для діагностики. Якщо застосунок, що дає збій, працює в `staging`, то Под для діагностики в `default` має інший перший пошуковий домен і може проґавити саме ту неоднозначність, що спричиняє збій. Створюйте діагностичний Под у тому самому просторі імен, якщо ви навмисно не порівнюєте простори імен. Ця одна звичка ловить багато помилок, де `api` означає один Сервіс для застосунку й інший Сервіс для інженера, який виконує разові команди.

Не ігноруйте негативні докази від успішних пошуків. Якщо повний FQDN розв'язується, а повернутий IP збігається з ClusterIP Сервісу, DNS виконав свою роботу для цього імені в цей момент. Подальший перезапуск CoreDNS після цього марнує час і може порушити роботу інших навантажень. Переходьте до селекторів Сервісу, EndpointSlices, цільових портів, готовності та політик. Діагностика DNS найцінніша тоді, коли вона каже вам, коли припинити діагностику DNS.

Поведінка клієнта може ускладнити чисте лабораторне міркування. Деякі застосунки кешують DNS-відповіді довше за TTL DNS, деякі повторюють спроби з власними бібліотеками резолвера, а деякі пули з'єднань продовжують використовувати старі адреси, доки з'єднання не будуть перевикористані. Коли інструменти командного рядка показують виправлену відповідь, а застосунок усе одно дає збій, порівняйте поведінку DNS середовища виконання застосунку, перевикористання з'єднань і час розгортання. Рівень DNS кластера може вже бути виправлений, тоді як процес навантаження ще потребує перезапуску чи перезавантаження конфігурації.

Логи CoreDNS варто інтерпретувати з огляду на обсяг запитів. Тихий лог не є доказом того, що клієнти не роблять запитів; Corefile може не логувати успішні запити. Шумний лог під час збою може бути корисним, але повторювані повідомлення з одного простору імен можуть приховувати ширший патерн. Поєднуйте логи з цілеспрямованими запитами з Пода для діагностики та перевіркою об'єктів через API Kubernetes, щоб не читати окремі рядки логів як усю історію.

```bash
# Inspect Service and EndpointSlice state after DNS succeeds.
kubectl get svc web-svc -n default
kubectl get endpointslices -n default -l kubernetes.io/service-name=web-svc
kubectl describe svc web-svc -n default
```

## Політики DNS, записи Подів та SRV-пошуки

Політика DNS Пода вирішує, що kubelet запише у файл резолвера Пода. Більшість Подів використовують `ClusterFirst`, що означає перевагу DNS кластера, тоді як зовнішні імена все одно можуть переспрямовуватися через CoreDNS. `Default` означає, що Под успадковує налаштування резолвера вузла, що корисно для рідкісних навантажень, схожих на хост, але зазвичай неправильно для застосунків, яким потрібні імена Сервісів. `None` означає, що ви самі надаєте конфігурацію DNS через `dnsConfig`.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: dns-policy-demo
spec:
  dnsPolicy: ClusterFirst
  containers:
  - name: app
    image: nginx
```

| Політика | Поведінка | Застосовуйте обережно, коли |
|--------|----------|--------------------|
| `ClusterFirst` | Використовує DNS кластера для імен кластера й переспрямовує зовнішні імена через CoreDNS | Усталена для звичайних Подів |
| `Default` | Використовує налаштування DNS вузла | Под навмисно має поводитися як резолвер вузла |
| `ClusterFirstWithHostNet` | Використовує DNS кластера навіть за `hostNetwork: true` | Подам із мережею хоста все одно потрібне виявлення Сервісів |
| `None` | Використовує лише налаштування DNS, які ви надаєте в `dnsConfig` | Вам потрібні власні nameservers, пошуки чи опції резолвера |

Поди з мережею хоста — поширена пастка DNS, бо вони ділять простір імен мережі вузла. Якщо ви поєднуєте `hostNetwork: true` з неправильною політикою DNS, зовнішні імена можуть працювати через резолвер вузла, тоді як імена Сервісів Kubernetes не спрацьовують. Ця асиметрія є підказкою: Под може розв'язувати публічні імена, але він не запитує CoreDNS про імена `*.svc.cluster.local`.

```yaml
# Pod using host network while still using cluster DNS.
apiVersion: v1
kind: Pod
metadata:
  name: host-network-pod
spec:
  hostNetwork: true
  dnsPolicy: ClusterFirstWithHostNet
  containers:
  - name: app
    image: nginx
```

Власні налаштування DNS є допустимими, але вони мають бути вузькими й навмисними. Встановлення `dnsPolicy: None` з публічними nameservers на кшталт `1.1.1.1` чи `8.8.8.8` може змусити зовнішній DNS працювати, але зламає виявлення Сервісів, бо ці публічні резолвери не знають домену вашого кластера Kubernetes. Якщо вам потрібні власні опції на кшталт нижчого значення `ndots`, поміркуйте, чи можете ви зберегти nameserver кластера замість того, щоб замінювати весь шлях резолвера.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: custom-dns
spec:
  dnsPolicy: "None"
  dnsConfig:
    nameservers:
    - 1.1.1.1
    - 8.8.8.8
    searches:
    - custom.local
    - svc.cluster.local
    options:
    - name: ndots
      value: "2"
  containers:
  - name: app
    image: nginx
```

Що сталося б, якби ви встановили `dnsPolicy: Default` на Поді й потім спробували розв'язати `my-service.default.svc.cluster.local`? Це залежить від резолвера вузла, але безпечне очікування — збій, якщо резолвер вузла не налаштований переспрямовувати домени кластера в CoreDNS. Звичайні вузли зазвичай не знають записів Сервісів Kubernetes, тож `Default` відводить Под від DNS-шляху кластера, який і забезпечує роботу виявлення Сервісів.

Іменовані порти й SRV-записи з'єднують DNS із виявленням портів. Сервіс із `name: http` на TCP-порту може дати SRV-відповідь під `_http._tcp.<service>.<namespace>.svc.cluster.local`. Багато HTTP-застосунків усе ще використовують звичайні пошуки A чи AAAA плюс налаштовані порти, але SRV-записи корисні в системах, які динамічно виявляють вузли-учасники й порти. Для CKA знайте, як розпізнати форму запису й чому іменований порт є обов'язковим.

```yaml
# Service with a named port.
apiVersion: v1
kind: Service
metadata:
  name: web-svc
spec:
  selector:
    app: web
  ports:
  - name: http
    port: 80
    targetPort: 8080
```

```bash
# SRV record format:
# _<port-name>._<protocol>.<service>.<namespace>.svc.cluster.local
# From a netshoot (or other dig-equipped) pod:
dig SRV _http._tcp.web-svc.default.svc.cluster.local
```

За кожною зміною політики DNS ховається проєктний компроміс. Зниження `ndots` може зменшити марні спроби пошукових доменів для зовнішніх імен, але водночас може змінити порядок пошуку для відносних імен, на які застосунки вже покладаються. Заміна nameservers може задовольнити особливу вимогу відповідності чи мережі, але може прибрати CoreDNS зі шляху. Використання мережі хоста може бути необхідним для агентів рівня вузла, але це змушує вас обрати `ClusterFirstWithHostNet`, коли агенту також потрібне виявлення Сервісів.

Найбезпечніше усталене значення — залишати звичайні навантаження на `ClusterFirst`. Більшості Подів застосунків виявлення Сервісів потрібне більше, ніж прямий доступ до поведінки резолвера вузла, а CoreDNS усе одно може переспрямовувати зовнішні імена. Тягніться до `Default` лише тоді, коли навантаження навмисно поводиться як програмне забезпечення на вузлі, і задокументуйте, що імена Сервісів кластера можуть не розв'язуватися. Тягніться до `None` лише тоді, коли можете назвати кожен nameserver, пошуковий суфікс та опцію, за які берете на себе відповідальність.

Політика DNS також взаємодіє із засобами контролю безпеки. NetworkPolicy може дозволяти трафік застосунку, але випадково блокувати UDP- й TCP-порт 53 від Подів до CoreDNS, або блокувати вихід CoreDNS до вищих резолверів. Симптом змінюється залежно від того, яку ланку заблоковано: імена кластера можуть давати тайм-аут з обраних просторів імен, або зовнішні імена можуть не спрацьовувати, тоді як імена Сервісів працюють. Коли в гру вступають політики, навмисно включайте DNS-трафік до дозволених шляхів, а не припускайте, що він завжди винятковий.

Для StatefulSet DNS-ідентичність є частиною контракту навантаження. Учасник бази даних чи брокер черги може потребувати знати імена вузлів-учасників на кшталт `web-0` і `web-1`, а headless-Сервіс надає цим ідентичностям стабільну DNS-форму. Це не означає, що кожен клієнт StatefulSet має повністю оминати Сервіси. Використовуйте стабільні імена Подів для протоколів між учасниками, яким вони потрібні, і використовуйте звичайні Сервіси, коли клієнтам просто потрібно дістатися будь-якого справного екземпляра.

SRV-записи потужні саме тому, що містять більше за адресу, але багато застосунків не запитують їх за замовчуванням. Якщо система очікує виявлення через SRV, переконайтеся, що порт Сервісу має стабільне ім'я, а клієнт справді запитує форму SRV-запису. Якщо система очікує звичайний A-запис, додавання іменованого порту магічно не навчить клієнта виявляти порти. DNS може публікувати інформацію лише у форматах, які клієнт уміє читати.

## Патерни та антипатерни

Використовуйте DNS-імена як частину явного контракту сервісу. Застосунок у межах того самого простору імен може використовувати короткі імена, коли простір імен є межею власності, але спільні платформові компоненти й клієнти між просторами імен мають надавати перевагу іменам із кваліфікацією простору імен. Цей патерн працює, бо робить залежність видимою в конфігурації, зменшує випадкове затінення Сервісами з однаковим іменем і дає рецензентам чітке місце для оцінки того, чи навмисна прив'язка до простору імен.

| Патерн | Коли його застосовувати | Чому він працює | Зауваження щодо масштабування |
|---------|----------------|--------------|-----------------------|
| Імена Сервісів із кваліфікацією простору імен | Спільні залежності та виклики між командами | Уникає випадкового розв'язання в межах того самого простору імен | Задокументуйте простір імен-власник і життєвий цикл |
| Повні FQDN у діагностиці | Реагування на інциденти та завдання CKA | Усуває неоднозначність пошукового домену | Скоригуйте, якщо домен кластера не `cluster.local` |
| Headless-Сервіс для стабільних учасників | StatefulSets і виявлення вузлів-учасників | Повертає ідентичності endpoints замість одного віртуального IP | Клієнти мають обробляти кілька адрес і плинність |
| Зміна CoreDNS із відкатом | Загальнокластерне налаштування DNS | Обмежує радіус ураження й покращує відновлення | Збережіть попередній ConfigMap і одразу перевірте основні імена |

Ще один сильний патерн — діагностувати DNS із того простору імен, де працює навантаження. Пошукові домени чутливі до простору імен, тож пошук із `default` може довести неправильне для застосунку в `payments`, `staging` чи `team-a`. Створіть тимчасовий Под у цільовому просторі імен, розв'яжіть те саме ім'я, що використовує застосунок, а потім розв'яжіть повний FQDN, щоб порівняти неоднозначність із явним наміром.

```bash
kubectl run dns-test -n staging --rm -it --image=busybox:1.36 --restart=Never -- \
  nslookup api-service

kubectl run dns-test -n staging --rm -it --image=busybox:1.36 --restart=Never -- \
  nslookup api-service.production.svc.cluster.local
```

Уникайте трактування CoreDNS як першого місця для виправлення кожної проблеми зі зв'язністю. Команди потрапляють у цей антипатерн, бо повідомлення про помилку згадує ім'я хоста, а DNS легше змінити централізовано, ніж конфігурацію застосунку. Кращою альтернативою є класифікувати збій за відповіддю: `NXDOMAIN`, тайм-аут, `SERVFAIL`, неправильний IP чи збій з'єднання після розв'язання. Ця класифікація каже вам, чи перевіряти імена, CoreDNS, доступність мережі, вище переспрямування, селектори Сервісу чи порти застосунку.

| Антипатерн | Що йде не так | Краща альтернатива |
|--------------|-----------------|--------------------|
| Використання політики DNS `Default` для звичайних Подів | Імена Сервісів перестають розв'язуватися, бо використовується резолвер вузла | Залишайте `ClusterFirst`, якщо Поду справді не потрібен DNS вузла |
| Покладання на короткі імена між просторами імен | Клієнти можуть несподівано дістатися локального Сервісу з однаковим іменем | Використовуйте `service.namespace` або повний FQDN |
| Редагування CoreDNS без відкату | Одна друкарська помилка може зламати загальнокластерне виявлення | Спершу експортуйте ConfigMap і перевірте одразу після зміни |
| Видалення `fallthrough` із власних плагінів | Незбіжні імена зупиняються до того, як відповіли плагіни Kubernetes чи переспрямування | Зберігайте fallthrough там, де пізніші плагіни мають обробляти промахи |
| Діагностика з неправильного простору імен | Результати пошукового домену не збігаються з ураженим навантаженням | Запускайте тимчасові Поди для діагностики у просторі імен навантаження |
| Припущення, що успіх DNS доводить зв'язність застосунку | Запит усе одно може дати збій на селекторах Сервісу, портах, політиці чи стані застосунку | Слідом за розв'язанням перевіряйте endpoint і з'єднання |

Найнадійніша операційна модель консервативна: використовуйте рідні для Kubernetes імена Сервісів для звичайного виявлення, тримайте власні правила CoreDNS малими, моніторте стан і помилки CoreDNS та залишайте перевизначення політики DNS для навантажень, яким вони справді потрібні. Це не робить DNS нудним. Це робить DNS передбачуваним, а саме цього ви хочете від системи, від якої залежить кожен мікросервіс, перш ніж зможе викликати будь-що інше.

## Каркас прийняття рішень

Обирайте найвужчу зміну DNS, яка розв'язує саме доведену вами проблему. Якщо проблема — неоднозначне ім'я, змініть конфігурацію застосунку на ім'я з кваліфікацією простору імен. Якщо проблема — відсутній запис Сервісу, виправте Сервіс чи простір імен. Якщо проблема — зовнішнє переспрямування, перевірте плагін `forward` у Corefile та доступність вищого DNS. Якщо проблема — файл резолвера одного Пода, перевірте `dnsPolicy`, `dnsConfig` і чи не змінила мережа хоста очікувану поведінку.

```text
Start with the failing name
    │
    ├── Does the full Service FQDN resolve from the affected namespace?
    │       │
    │       ├── Yes -> Short-name/search behavior or app config is suspect
    │       └── No  -> Check Service existence, namespace, endpoints, and CoreDNS
    │
    ├── Does kubernetes.default.svc.cluster.local resolve?
    │       │
    │       ├── Yes -> CoreDNS Kubernetes path works for at least one known Service
    │       └── No  -> Check CoreDNS Pods, Service endpoints, logs, and client resolv.conf
    │
    ├── Do external names fail while cluster names work?
    │       │
    │       ├── Yes -> Check CoreDNS forward plugin and upstream DNS egress
    │       └── No  -> Continue testing the application path after DNS
    │
    └── Is only one Pod affected?
            │
            ├── Yes -> Inspect dnsPolicy, dnsConfig, hostNetwork, and resolv.conf
            └── No  -> Treat CoreDNS, Service naming, or network policy as shared suspects
```

| Ситуація | Надавайте перевагу цьому | Уникайте цього | Причина |
|-----------|-------------|------------|--------|
| Виклик застосунок-до-застосунку в одному просторі імен | Коротке ім'я Сервісу | Повний домен усюди за звичкою | Короткі імена читабельні, коли власність простору імен зрозуміла |
| Залежність між просторами імен | `service.namespace` або повний FQDN | Голе ім'я Сервісу | Пошукові домени спершу пробують простір імен викликача |
| Агенту з мережею хоста потрібні Сервіси | `ClusterFirstWithHostNet` | `Default` випадково | Мережа хоста змінює успадкування резолвера |
| Затримка зовнішнього імені через багато спроб пошуку | Перегляньте `ndots` і поведінку завершальної крапки | Заміна CoreDNS цілком | Проблема може бути в порядку пошуку, а не у збої DNS |
| Застаріле внутрішнє ім'я для всіх Подів | Невелике правило `hosts` чи `forward` у CoreDNS із відкатом | Жорстко закодовані хаки на рівні Пода | Загальнокластерне правило підтримуване, коли вузько обмежене |
| Стабільна ідентичність вузла-учасника | Headless-Сервіс плюс іменування StatefulSet | Посилання на випадковий IP Пода | Стабільна DNS-ідентичність відповідає семантиці навантаження |

Цей каркас навмисно практичний для Kubernetes 1.35 і стилю діагностики CKA. На іспиті вас зазвичай не просять спроєктувати глобальну корпоративну DNS-архітектуру; вас просять довести, чому ім'я Сервісу розв'язується чи ні, і виправити найменшу зламану частину. Той самий підхід масштабується на продакшен, бо уникає широких змін, доки докази не вкажуть на спільний компонент DNS.

Коли ви під тиском часу, надавайте перевагу питанням, які чітко ділять простір проблеми. «Чи може цей Под розв'язати `kubernetes.default.svc.cluster.local`?» відокремлює базовий DNS-шлях кластера від специфічного для застосунку імені. «Чи може він розв'язати повний FQDN?» відокремлює існування Сервісу від поведінки пошукового домену. «Чи має Сервіс EndpointSlices?» відокремлює DNS від доставлення трафіку. Ці питання швидші за запам'ятовування довгих послідовностей команд, бо кожна відповідь змінює ваш наступний крок.

Для проєктних оглядів записуйте рішення щодо DNS тією самою мовою, яку ви використовуєте для власності й доменів збоїв. Коротке ім'я каже, що залежність локальна для простору імен. Ім'я з кваліфікацією простору імен каже, що залежністю володіє інший простір імен. Headless-Сервіс каже, що клієнтам дозволено бачити окремі endpoints. Налаштування CoreDNS каже, що платформа володіє загальнокластерним правилом іменування. Робити ці значення явними — означає не дати DNS перетворитися на випадкову архітектурну діаграму, яку ніхто не погоджувався підтримувати.

## Чи знали ви?

- **CoreDNS став усталеним DNS-додатком приблизно у проміжку Kubernetes 1.11**: kube-dns був початковим DNS-додатком кластера, тоді як CoreDNS приніс меншу архітектуру на основі плагінів, яку легше розширювати й перевіряти через Corefile.
- **Сервіс DNS часто все ще називається `kube-dns`, навіть коли Поди працюють на CoreDNS**: ця назва-сумісник зберігає роботу старіших припущень, тож команди діагностики мають перевіряти ім'я Сервісу й Поди CoreDNS, що стоять за ним, разом.
- **Поди Kubernetes зазвичай отримують `ndots:5` у `/etc/resolv.conf`**: імена з менш ніж п'ятьма крапками можуть пробуватися через пошукові домени кластера до остаточного абсолютного запиту, що може впливати на затримку зовнішнього DNS.
- **SRV-записи потребують іменованих портів Сервісу**: порт Сервісу з іменем `http` може дати `_http._tcp.service.namespace.svc.cluster.local`, але неіменований порт не дає DNS стабільної мітки порту для публікації.

## Типові помилки

| Помилка | Чому вона виникає | Як її виправити |
|---------|----------------|---------------|
| Використання голого імені Сервісу для залежності між просторами імен | Пошукові домени спершу пробують простір імен викликача, тож локальний Сервіс із однаковим іменем може затінити потрібну ціль | Використовуйте `service.namespace` або повний FQDN у конфігурації між просторами імен |
| Припущення, що CoreDNS справний, бо Поди працюють | Под, що виглядає готовим, усе одно може мати помилки Corefile, проблеми спостереження за API чи відсутні корисні endpoints Сервісу | Протестуйте відоме ім'я кластера, перевірте endpoints `kube-dns` і прочитайте логи CoreDNS |
| Встановлення `dnsPolicy: Default` на звичайних Подах застосунку | Под успадковує поведінку резолвера вузла й може перестати розв'язувати імена `*.svc.cluster.local` | Залишайте `ClusterFirst`, якщо вам навмисно не потрібні налаштування DNS вузла |
| Забування `ClusterFirstWithHostNet` для Подів із мережею хоста | Мережа хоста змінює успадкування резолвера, тож зовнішні імена можуть працювати, тоді як імена Сервісів не спрацьовують | Встановіть `dnsPolicy: ClusterFirstWithHostNet`, коли Подам із мережею хоста все одно потрібен DNS кластера |
| Редагування ConfigMap CoreDNS без збереження `fallthrough` | Власний плагін може повернути `NXDOMAIN` до того, як пізніші плагіни оброблять звичайні імена кластера | Зберігайте `fallthrough` там, де нерозв'язані імена мають продовжувати рух ланцюжком плагінів |
| Трактування тайм-ауту як доказу збою DNS | Тайм-аути можуть статися після розв'язання DNS через селектори, порти, NetworkPolicy чи стан застосунку | Спершу розв'яжіть ім'я, потім перевірте EndpointSlices, порти Сервісу та фактичну зв'язність |
| Безтурботна заміна nameservers кластера в `dnsConfig` | Публічні чи вузлові резолвери не знають записів Сервісів Kubernetes | Збережіть шлях CoreDNS або задокументуйте, чому Под має відмовитися від виявлення кластера |

## Тест

<details>
<summary>Питання 1: Ваша команда повідомляє, що `curl api` з простору імен `team-a` дістається неправильного застосунку після того, як інша команда створила Сервіс `api` локально. Що слід перевірити й змінити?</summary>

Почніть з підтвердження простору імен викликача та пошукових доменів у `/etc/resolv.conf` ураженого Пода, бо `api` — відносне ім'я. Резолвер спробує `api.team-a.svc.cluster.local` перед будь-якою іншою формою з кваліфікацією простору імен, тож локальний Сервіс може затінити потрібну залежність. Змініть конфігурацію застосунку на `api.shared` чи `api.shared.svc.cluster.local`, а потім перевірте розв'язану адресу з Пода для діагностики в `team-a`. Не латайте для цього CoreDNS першим, бо система DNS поводиться згідно зі звичайними правилами пошукових доменів.

</details>

<details>
<summary>Питання 2: Після оновлення кластера застосунки не можуть розв'язати імена Сервісів, але `kubectl get pods -n kube-system -l k8s-app=kube-dns` показує запущені Поди CoreDNS. Який ваш наступний діагностичний шлях?</summary>

Запущені Поди — це лише один факт, тож перевірте, чи відповідає CoreDNS на відоме ім'я на кшталт `kubernetes.default.svc.cluster.local` зсередини кластера. Потім перевірте endpoints Сервісу `kube-dns`, логи CoreDNS і `/etc/resolv.conf` Пода, що дає збій, щоб переконатися, що клієнт використовує очікуваний nameserver. Якщо логи CoreDNS показують помилки Corefile чи спостереження за API, зосередьтеся на конфігурації й доступі до площини управління. Якщо відоме ім'я розв'язується, рухайтеся в бік конкретного імені Сервісу, простору імен і стану EndpointSlice замість сліпого перезапуску DNS.

</details>

<details>
<summary>Питання 3: Ви додали запис `hosts` у CoreDNS для `legacy-api.internal`, і раптом звичайні імена Сервісів повертають `NXDOMAIN`. Що, найімовірніше, пішло не так?</summary>

Власному блоку `hosts`, імовірно, бракує `fallthrough`, або його розташовано так, що він зупиняє незбіжні запити до того, як плагін `kubernetes` може відповісти. Плагін `hosts` може відповідати на одне ім'я, яке ви додали, повертаючи негативні відповіді для імен, яких він не знає. Відновіть попередній ConfigMap або додайте `fallthrough`, перезапустіть чи дочекайтеся перезавантаження та одразу перевірте і `legacy-api.internal`, і `kubernetes.default.svc.cluster.local`. Ключовий урок у тому, що вузьке власне правило все одно перебуває у спільному DNS-шляху кластера.

</details>

<details>
<summary>Питання 4: Агент моніторингу з мережею хоста розв'язує `example.com`, але не може розв'язати `kubernetes.default.svc.cluster.local`. Яку політику DNS слід оцінити?</summary>

Оцініть, чи використовує Под `hostNetwork: true` без `dnsPolicy: ClusterFirstWithHostNet`. Зовнішній DNS може працювати через резолвер вузла, тоді як імена Сервісів кластера не спрацьовують, бо резолвер вузла зазвичай не знає записів DNS Kubernetes. Встановіть `ClusterFirstWithHostNet`, коли агенту потрібні і мережа хоста, і виявлення сервісів кластера. Після зміни перевірте `/etc/resolv.conf` Пода, щоб довести, що IP Сервісу CoreDNS присутній.

</details>

<details>
<summary>Питання 5: Под успішно розв'язує `web.default.svc.cluster.local`, але HTTP-запити до `web:8080` дають тайм-аут. Чому слід уникати зміни CoreDNS першою?</summary>

Успішне розв'язання доводить, що DNS не є першим зламаним рівнем для цього імені. Тайм-аут може спричинятися невідповідністю targetPort Сервісу, порожніми чи неготовими endpoints, NetworkPolicy чи застосунком, який не слухає на очікуваному порту. Перевірте Сервіс, EndpointSlices, обрані Поди й прямий тест з'єднання, перш ніж чіпати CoreDNS. Зміна DNS після успішного пошуку ризикує додати загальнокластерну проблему, не усуваючи фактичного збою мережі чи застосунку.

</details>

<details>
<summary>Питання 6: Зовнішні пошуки на кшталт `api.example.com` повільні з Подів, тоді як пошуки Сервісів кластера швидкі. Яку поведінку резолвера слід дослідити?</summary>

Дослідіть розгортання пошукових доменів і опцію `ndots` у `/etc/resolv.conf` Пода. За поширеного налаштування `ndots:5` ім'я на кшталт `api.example.com` може пробуватися через пошукові домени кластера до того, як остаточний абсолютний запит увінчається успіхом. Залежно від застосунку та бібліотеки резолвера використання завершальної крапки для абсолютних імен чи коригування `dnsConfig.options.ndots` може зменшити марні пошуки. Тримайте виправлення обмеженим, бо глобальне зниження `ndots` може змінити поведінку для відносних імен кластера.

</details>

<details>
<summary>Питання 7: StatefulSet потребує, щоб кожна репліка виявляла стабільні ідентичності вузлів-учасників замість одного спільного ClusterIP. Який DNS-патерн підходить і що мають обробляти клієнти?</summary>

Використовуйте headless-Сервіс зі StatefulSet, щоб кожен Под отримував передбачувану DNS-ідентичність на кшталт `web-0.web-svc.default.svc.cluster.local`. Цей патерн підходить для виявлення вузлів-учасників, бо DNS може експонувати окремі ідентичності endpoints замість одного віртуального IP Сервісу. Клієнти мають обробляти кілька адрес, зміни endpoints та можливість того, що вузол-учасник ще не готовий. Для звичайного трафіку без стану звичайний Сервіс ClusterIP зазвичай простіший, бо приховує ці деталі.

</details>

## Практична вправа

Сценарій вправи: ви — черговий інженер навчального кластера, і розробник каже, що імена Сервісів ненадійні. Ваше завдання — довести нормальний DNS-шлях, створити Сервіси, які демонструють поведінку в межах того самого простору імен і між просторами імен, перевірити CoreDNS, а потім прибрати за собою, не залишивши тестових ресурсів. Виконуйте команди з оболонки, де `kubectl` уже вказує на одноразовий кластер Kubernetes 1.35 чи новіший.

> **Примітка:** Пошукові домени DNS Kubernetes можуть розгортати `service.namespace` у `service.namespace.svc.cluster.local`, але BusyBox `nslookup` в `busybox:1.36` не застосовує цього розгортання з двох міток і може вивести `NXDOMAIN` для імен на кшталт `web.default`. BusyBox `nslookup` також завершується з ненульовим кодом навіть тоді, коли вивів корисну відповідь `Name:` і `Address:` для потрібного запису, тож оцінюйте його успіх за показаним записом, а не лише за кодом виходу Пода. Для перевірки з кваліфікацією простору імен використовуйте `wget -qO- --timeout=2 http://<name>.<ns>/`, запитуйте повний FQDN через `nslookup` або запустіть netshoot-под із `host` чи `dig`.

### Завдання 1: Перевірте базову лінію DNS кластера

Почніть з перевірки спільних компонентів DNS перед створенням ресурсів навантаження. Це дає вам базову лінію для подальших збоїв і навчає, які об'єкти задіяні в DNS-шляху. Якщо ваше середовище використовує інші мітки для CoreDNS, адаптуйте селектор після перевірки Подів у `kube-system`.

```bash
kubectl get pods -n kube-system -l k8s-app=kube-dns
kubectl get svc -n kube-system kube-dns
kubectl get endpoints kube-dns -n kube-system
kubectl get configmap coredns -n kube-system -o yaml
```

<details>
<summary>Примітки до розв'язання</summary>

Ви маєте побачити принаймні один готовий Под CoreDNS, Сервіс `kube-dns` і endpoints за цим Сервісом. ConfigMap має містити Corefile із плагіном `kubernetes` для домену кластера й плагіном `forward` для нерозв'язаних імен. Якщо у Сервісу немає endpoints, виправте доступність CoreDNS, перш ніж продовжувати, бо клієнти не мають справного DNS-бекенда.

</details>

### Завдання 2: Створіть Сервіс і розв'яжіть його імена

Створіть простий Deployment і експонуйте його як Сервіс. Потім запитайте коротке ім'я, ім'я з кваліфікацією простору імен та повний FQDN із тимчасових Подів. Мета не в тому, щоб перевірити вміст nginx; мета — поспостерігати, як різні імена розв'язуються через той самий запис Сервісу.

```bash
kubectl create deployment web --image=nginx
kubectl expose deployment web --port=80
kubectl get svc web
```

```bash
kubectl run test1 --rm -it --image=busybox:1.36 --restart=Never -- \
  nslookup web

kubectl run test2 --rm -it --image=busybox:1.36 --restart=Never -- \
  wget -qO- --timeout=2 http://web.default/

kubectl run test3 --rm -it --image=busybox:1.36 --restart=Never -- \
  nslookup web.default.svc.cluster.local
```

<details>
<summary>Примітки до розв'язання</summary>

Команди `nslookup` для короткого імені й повного FQDN мають вивести ClusterIP Сервісу для звичайного Сервісу ClusterIP, а команда `wget` перевіряє, що форма з кваліфікацією простору імен `web.default` працює через клієнт із резолвером. Специфікація DNS Kubernetes розгортає `service.namespace`, але BusyBox `nslookup` повідомляє `NXDOMAIN` для цієї форми з двох міток, тож перевіряйте її резолвером у стилі libc на кшталт `wget`, повним `nslookup` із FQDN або командою `host` чи `dig` у netshoot, перш ніж звинувачувати CoreDNS. Якщо працює лише повний FQDN, перевірте список пошуку резолвера тимчасового Пода.

</details>

### Завдання 3: Перевірте конфігурацію резолвера Пода

Використайте тимчасовий Под, щоб прочитати налаштування резолвера, які впроваджує kubelet. Це робить поведінку пошукового домену видимою, а не трактує її як прихований трюк резолвера. Зверніть увагу на nameserver, список пошуку та опцію `ndots`.

```bash
kubectl run test-resolv --rm -it --image=busybox:1.36 --restart=Never -- \
  cat /etc/resolv.conf
```

<details>
<summary>Примітки до розв'язання</summary>

Nameserver має бути ClusterIP Сервісу `kube-dns`, а список пошуку має містити домен `svc` поточного простору імен, за яким ідуть ширші домени кластера. Якщо nameserver не є IP Сервісу DNS, перевірте, чи задіяна власна політика DNS або мережа хоста. Це спостереження часто є найшвидшим способом пояснити, чому один Под поводиться інакше за інший.

</details>

### Завдання 4: Протестуйте розв'язання між просторами імен

Створіть другий простір імен і Сервіс з іншим іменем. Запитайте його з простору імен default, використовуючи форму з кваліфікацією простору імен. Це показує, чому залежності між просторами імен мають бути явними в конфігурації.

```bash
kubectl create namespace other
kubectl create deployment db -n other --image=nginx
kubectl expose deployment db -n other --port=80
kubectl get svc db -n other
```

```bash
kubectl run test4 --rm -it --image=busybox:1.36 --restart=Never -- \
  wget -qO- --timeout=2 http://db.other/
```

<details>
<summary>Примітки до розв'язання</summary>

Запит із кваліфікацією простору імен має розв'язатися, бо специфікація DNS Kubernetes дозволяє `db.other` розгортатися в `db.other.svc.cluster.local`, а команда `wget` перевіряє цю поведінку пошуком у стилі застосунку. BusyBox `nslookup db.other` повідомить `NXDOMAIN` для цієї форми з двох міток, тож використовуйте резолвер у стилі libc на кшталт `wget`, повний FQDN чи netshoot-под, коли вам потрібно довести розв'язання з кваліфікацією простору імен. Якщо `nslookup db` із `default` дає збій чи дістається іншого Сервісу, це очікувана поведінка пошукового домену. Виправлення для реальних застосунків — явне іменування, а не латка CoreDNS.

</details>

### Завдання 5: Порівняйте зовнішній DNS і логи CoreDNS

Тепер протестуйте зовнішнє ім'я й перевірте логи CoreDNS. Це відокремлює поведінку плагіна Kubernetes від поведінки вищого переспрямування. Використовуйте безпечний для документації домен для прикладів замість залежності від конкретного імені публічного сервісу.

```bash
kubectl run test5 --rm -it --image=busybox:1.36 --restart=Never -- \
  nslookup example.com

kubectl logs -n kube-system -l k8s-app=kube-dns --tail=20
```

<details>
<summary>Примітки до розв'язання</summary>

Якщо імена Сервісів кластера розв'язуються, а `example.com` дає збій, зосередьтеся на плагіні `forward` CoreDNS і доступності вищого DNS. Якщо і імена кластера, і зовнішні імена дають збій, спершу перевірте стан CoreDNS, endpoints, логи та конфігурацію резолвера клієнта. Логи можуть бути тихими у справних кластерах, якщо не ввімкнено логування помилок або не стався збій.

</details>

### Завдання 6: Відпрацюйте DNS headless-Сервісу

Створіть невелике навантаження й headless-Сервіс, щоб DNS повертав адреси endpoints, а не один ClusterIP. Це закріплює різницю між виявленням за віртуальним IP Сервісу та прямим виявленням endpoints. Не використовуйте цей патерн для кожного застосунку; він найдоречніший, коли клієнти розуміють ідентичності вузлів-учасників.

```bash
kubectl create deployment headless-test --image=nginx --replicas=3
```

```bash
cat << 'EOF' | kubectl apply -f -
apiVersion: v1
kind: Service
metadata:
  name: headless-svc
spec:
  clusterIP: None
  selector:
    app: headless-test
  ports:
  - port: 80
EOF
```

```bash
kubectl wait --for=condition=ready pod -l app=headless-test --timeout=60s

kubectl run test6 --rm -it --image=busybox:1.36 --restart=Never -- \
  nslookup headless-svc
```

<details>
<summary>Примітки до розв'язання</summary>

Пошук має повернути IP-адреси endpoints, а не один ClusterIP Сервісу. Якщо ви не отримуєте корисної відповіді, перевірте, чи готові Поди і чи збігається селектор Сервісу з їхніми мітками. Headless DNS залежить від endpoints, тож помилки селектора виявляються швидко.

</details>

### Завдання 7: Перевірте власну політику DNS

Створіть Под, який відмовляється від нормального DNS-шляху кластера. Це навмисно контрастна вправа: вона показує, чому `dnsPolicy: None` може зламати виявлення Сервісів, якщо ви заміните nameserver резолверами, які не знають записів Kubernetes.

```bash
cat << 'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: custom-dns-pod
spec:
  dnsPolicy: None
  dnsConfig:
    nameservers:
    - 8.8.8.8
    searches:
    - custom.local
    options:
    - name: ndots
      value: "2"
  containers:
  - name: app
    image: busybox:1.36
    command: ["sleep", "3600"]
EOF
```

```bash
kubectl wait --for=condition=ready pod/custom-dns-pod --timeout=60s
kubectl exec custom-dns-pod -- cat /etc/resolv.conf
kubectl exec custom-dns-pod -- nslookup kubernetes
```

<details>
<summary>Примітки до розв'язання</summary>

Файл резолвера має показати власний nameserver і пошуковий домен. Пошук `kubernetes` очікувано дасть збій у багатьох кластерах, бо публічний резолвер не знає DNS-зони кластера. Саме тому власна політика DNS має бути навмисною й задокументованою.

</details>

### Завдання 8: Прибирання

Видаліть ресурси, створені під час вправи. Прибирання важливе, бо тести DNS створюють Сервіси, простори імен і Поди, які можуть затінювати майбутні імена, якщо їх залишити. Виконуйте команди, навіть якщо одне з попередніх завдань дало збій, та ігноруйте помилки not-found лише після підтвердження, що ресурсу вже немає.

```bash
kubectl delete pod custom-dns-pod
kubectl delete deployment headless-test
kubectl delete svc headless-svc
kubectl delete deployment web
kubectl delete svc web
kubectl delete namespace other
```

### Критерії успіху

- [ ] Розв'язувати DNS-імена сервісів і Подів, використовуючи короткі імена, імена з кваліфікацією простору імен, FQDN, відповіді headless-Сервісу та міркування про записи у стилі SRV.
- [ ] Діагностувати збої DNS, порівнюючи Поди CoreDNS, endpoints `kube-dns`, логи CoreDNS, `/etc/resolv.conf` Пода, об'єкти Сервісів та EndpointSlices.
- [ ] Налаштовувати CoreDNS безпечно в письмовому плані, що містить `hosts`, `forward`, `fallthrough`, перевірку та відкат.
- [ ] Оцінювати політики DNS `ClusterFirst`, `Default`, `ClusterFirstWithHostNet` і `None` для звичайних Подів, Подів із мережею хоста та випадків власного резолвера.
- [ ] Пояснювати, коли DNS доведено справний, а коли решта збою належить селекторам Сервісу, портам, NetworkPolicy чи поведінці застосунку.

### Необов'язкові швидкісні дрилі

Ці дрилі необов'язкові, але вони зберігають практику швидких команд з оригінального модуля. Запускайте їх лише в одноразовому просторі імен чи навчальному кластері. Мета — напрацювати м'язову пам'ять, не замінюючи робочого процесу міркування вище.

```bash
# Drill 1: DNS basics.
kubectl create deployment dns-test --image=nginx
kubectl expose deployment dns-test --port=80
kubectl run test --rm -it --image=busybox:1.36 --restart=Never -- \
  sh -c 'nslookup dns-test; wget -qO- --timeout=2 http://dns-test.default/; nslookup dns-test.default.svc.cluster.local'
kubectl delete deployment dns-test
kubectl delete svc dns-test
```

```bash
# Drill 2: CoreDNS health.
kubectl get pods -n kube-system -l k8s-app=kube-dns -o wide
kubectl get svc kube-dns -n kube-system
kubectl get deployment coredns -n kube-system
kubectl logs -n kube-system -l k8s-app=kube-dns --tail=10
```

```bash
# Drill 3: Cross-namespace resolution.
kubectl create namespace ns1
kubectl create namespace ns2
kubectl create deployment app1 -n ns1 --image=nginx
kubectl create deployment app2 -n ns2 --image=nginx
kubectl expose deployment app1 -n ns1 --port=80
kubectl expose deployment app2 -n ns2 --port=80
kubectl run test -n ns1 --rm -it --image=busybox:1.36 --restart=Never -- \
  wget -qO- --timeout=2 http://app2.ns2/
kubectl run test -n ns2 --rm -it --image=busybox:1.36 --restart=Never -- \
  wget -qO- --timeout=2 http://app1.ns1/
kubectl delete namespace ns1 ns2
```

```bash
# Drill 4: Inspect Pod DNS config.
kubectl run dns-check --image=busybox:1.36 --command -- sleep 3600
kubectl wait --for=condition=ready pod/dns-check --timeout=60s
kubectl exec dns-check -- cat /etc/resolv.conf
kubectl get svc kube-dns -n kube-system -o jsonpath='{.spec.clusterIP}'
kubectl delete pod dns-check
```

```bash
# Drill 5: CoreDNS ConfigMap.
kubectl get configmap coredns -n kube-system -o jsonpath='{.data.Corefile}'
kubectl describe configmap coredns -n kube-system
kubectl get configmap coredns -n kube-system -o yaml | grep -E "kubernetes|forward|cache"
```

```bash
# Drill 6: Debug DNS failure workflow.
kubectl create deployment web --image=nginx
kubectl expose deployment web --port=80
kubectl run debug1 --rm -it --image=busybox:1.36 --restart=Never -- \

kubectl logs -n kube-system -l k8s-app=kube-dns --tail=5
kubectl delete deployment web
kubectl delete svc web
```
