## Що ви зможете зробити

Після цього модуля ви зможете:
- **Діагностувати** збої мережі Под'ів, розділяючи симптоми встановлення CNI, IPAM, маршрутизації на нодах, DNS, kube-proxy та мережевих політик.
- **Порівнювати** Calico, Cilium, Flannel, Canal та хмарні плагіни за підтримкою політик, моделлю маршрутизації, вартістю експлуатації й компромісами щодо продуктивності.
- **Трасувати** трафік у межах однієї ноди, між нодами та сервісний трафік крізь простори імен, veth-пари, мости, оверлеї, таблиці маршрутизації, kube-proxy та бекенд-Под'и.
- **Реалізувати** повторюваний робочий процес інспекції CNI за допомогою `kubectl`, файлів CNI на рівні ноди, команд мережі Под'а та тестів зв'язності сервісів.
- **Оцінювати**, коли варто застосовувати мережу хоста, порти хоста, режими kube-proxy та зміни CIDR, не порушуючи припущень рівня кластера.

## Чому цей модуль важливий

Гіпотетичний сценарій: команда ініціалізує кластер Kubernetes 1.35 за допомогою `kubeadm`, приєднує дві робочі ноди й одразу розгортає вебзастосунок разом із CoreDNS. На перший погляд ноди виглядають справними, але кожне нове робоче навантаження залишається у стані `ContainerCreating`, CoreDNS ніколи не стає готовим, а імена сервісів не вдається розрізнити, бо Под'и так і не отримують мережевих інтерфейсів. З YAML-описом Деплойменту все гаразд; бракує іншого рівня — плагіна CNI, який kubelet очікує викликати щоразу, коли пісочниці (sandbox) потрібна мережа Под'а.

CNI легко недооцінити, адже Kubernetes подає Под'и, Сервіси та мережеві політики як об'єкти API, тоді як фактичний шлях пакета здебільшого реалізують агенти на нодах і мережеві примітиви Linux. Сервіс може існувати без корисних ендпойнтів, мережеву політику API-сервер може прийняти, але встановлений плагін її не застосовуватиме, а Под може бути у стані `Running`, доки трафік між нодами тихо зникає у заблокованому оверлейному порту. Навичка рівня CKA полягає не в зазубрюванні набору команд одного плагіна; це вміння розташувати кожен симптом на правильній частині стека, перш ніж змінювати конфігурацію.

Уявіть CNI як департамент міського планування для трафіку Под'ів. Kubernetes каже, що кожна будівля повинна мати адресу, а кожен район — бути досяжним, але саме дизайн CNI вирішує, чи будуть вулиці простими місцевими дорогами, тунелями між районами, маршрутизованими магістралями чи маршрутами, що оголошуються через BGP. kube-proxy — це інша міська служба: він стежить за змінами Сервісів та EndpointSlice і програмує правила, що спрямовують трафік зі стабільної віртуальної адреси до мінливих бекенд-Под'ів. Цей модуль навчає, як ці обов'язки перетинаються, де вони навмисно не накладаються один на одного, і як інспектувати систему без здогадок.

Практична користь — упевненість в умовах неоднозначності. Коли власник робочого навантаження повідомляє, що «мережа лежить», ви маєте змогу попросити одне ім'я Под'а, одне ім'я ноди, один пункт призначення й одну команду, що дає збій, а потім перетворити ці деталі на сфокусований план тестування. Це і є різниця між реактивною зміною інфраструктури кластера й доведенням того, який саме контракт насправді порушено.

## Мережева модель Kubernetes та обов'язки CNI

Kubernetes починає з оманливо суворої мережевої моделі: кожен Под має могти спілкуватися з будь-яким іншим Под'ом без NAT, ноди мають могти спілкуватися з Под'ами, а IP, який Под бачить для самого себе, має збігатися з IP, за яким його дістають інші Под'и. Саме завдяки цій моделі маніфести застосунків можуть переміщуватися між нодами, не вшиваючи в себе адреси нод чи відображення портів. Вона ж пояснює, чому встановлення Kubernetes без робочого CNI лишає кластер недобудованим; kubelet може створювати контейнери, але не може під'єднати їх до мережевої моделі, яку обіцяє API.

Модель навмисно простіша за більшість фізичних мереж. Kubernetes не вимагає від команд застосунків вивчати підмережі нод, межі стійок, топологію груп безпеки чи протоколи тунелів, перш ніж вони розгорнуть Деплоймент. Натомість оператор кластера обирає мережеву реалізацію, яка робить кожен IP Под'а досяжним усередині кластера. Ця простота має свою ціну: коли реалізація ламається, API досі показує високорівневі об'єкти, тоді як справжній збій живе в інтерфейсах Linux, таблицях маршрутизації, рушіях політик або в досяжності між нодами.

```
┌────────────────────────────────────────────────────────────────┐
│                Kubernetes Network Requirements                  │
│                                                                 │
│   1. Pod-to-Pod: All pods can communicate with all pods        │
│      without NAT                                                │
│      ┌─────┐      ┌─────┐                                      │
│      │Pod A│◄────►│Pod B│  (direct IP, no NAT)                │
│      └─────┘      └─────┘                                      │
│                                                                 │
│   2. Node-to-Pod: Nodes can communicate with all pods          │
│      without NAT                                                │
│      ┌─────┐      ┌─────┐                                      │
│      │Node │◄────►│ Pod │  (direct access)                    │
│      └─────┘      └─────┘                                      │
│                                                                 │
│   3. Pod IP = Seen IP: The IP a pod sees is the same IP        │
│      others see                                                 │
│      Pod thinks: "My IP is 10.244.1.5"                         │
│      Others see: "Pod's IP is 10.244.1.5"                      │
│                                                                 │
│   4. Pod-to-Service: Pods can reach services by ClusterIP      │
│      ┌─────┐      ┌───────────┐      ┌─────┐                  │
│      │ Pod │─────►│  Service  │─────►│ Pod │                  │
│      └─────┘      └───────────┘      └─────┘                  │
│                                                                 │
└────────────────────────────────────────────────────────────────┘
```

CNI забезпечує ту частину обіцянки, що стосується Под'а. Коли kubelet створює пісочницю Под'а, передача керування між kubelet і середовищем виконання викликає налаштований плагін CNI, щоб під'єднати мережевий простір імен пісочниці, виділити IP-адресу через IPAM, створити інтерфейс із боку Под'а, з'єднати цей інтерфейс із мережею ноди та встановити достатньо маршрутів чи стану площини даних, щоб трафік міг за потреби покинути ноду. kube-proxy обробляє шлях віртуального IP Сервісу, CoreDNS відповідає за розрізнення імен, а хмарна чи апаратна мережа — за досяжність нод; плутати ці межі — найшвидший спосіб налагоджувати не той рівень.

Цей поділ праці особливо важливий під час іспитів, бо симптом часто згадує робоче навантаження, а не компонент. «Под не може дістатися сервісу» може означати, що Под не має IP, що сервіс не має ендпойнтів, що kube-proxy не зміг запрограмувати правила, що CoreDNS не повернув відповіді або що мережева політика блокує з'єднання. Дисциплінований відповідач запитує, яку саме частину шляху пакета вже доведено справною. Доки прямий трафік за IP Под'а не працює, тест сервісу чи DNS несе забагато припущень, щоб бути корисним.

| Обов'язок | Компонент |
|----------------|-----------|
| Виділення IP Под'а | Плагін CNI (IPAM) |
| Маршрутизація між Под'ами | Плагін CNI |
| Мережа між нодами | Плагін CNI |
| Застосування мережевих політик | Плагін CNI (якщо підтримується) |
| Маршрутизація ClusterIP Сервісу | kube-proxy |

Мережеві простори імен — це практичний механізм, що дозволяє кожному Под'у вважати, ніби він володіє інтерфейсом `eth0`, власними маршрутами та власною конфігурацією резолвера. У поширеному варіанті на основі моста kubelet і середовище виконання контейнерів створюють простір імен пісочниці, плагін CNI створює veth-пару, один її кінець з'являється як `eth0` усередині Под'а, а інший приєднується до моста з боку ноди, як-от `cni0`. Інші CNI можуть використовувати програми eBPF, маршрутизовані інтерфейси або хмарні еластичні мережеві інтерфейси, але ментальна модель усе одно корисна: мережу Под'а під'єднують у момент створення пісочниці, а не після того, як контейнер застосунку вирішить слухати порт.

Межа простору імен також пояснює, чому команди треба запускати з правильної точки зору. `ip addr` на ноді показує простір імен хоста й будь-які veth-інтерфейси чи інтерфейси площини даних із боку хоста; `kubectl exec <pod> -- ip addr` показує простір імен Под'а та лише ті інтерфейси, що видимі всередині цього Под'а. Коли ці два погляди розходяться, вони не суперечать один одному. Вони показують два боки одного й того ж приєднання — подібно до того, як дивитися на патч-корд із боку серверної стійки та з боку машини, під'єднаної до неї.

```
┌────────────────────────────────────────────────────────────────┐
│                   Network Namespaces                            │
│                                                                 │
│   Node                                                          │
│   ┌────────────────────────────────────────────────────────┐   │
│   │  Host Network Namespace                                 │   │
│   │  eth0: 192.168.1.10                                    │   │
│   │                                                         │   │
│   │     ┌─────────────────┐     ┌─────────────────┐        │   │
│   │     │ Pod A           │     │ Pod B           │        │   │
│   │     │ Network NS      │     │ Network NS      │        │   │
│   │     │                 │     │                 │        │   │
│   │     │ eth0:10.244.1.5 │     │ eth0:10.244.1.6 │        │   │
│   │     │                 │     │                 │        │   │
│   │     └────────┬────────┘     └────────┬────────┘        │   │
│   │              │                       │                  │   │
│   │              └───────────┬───────────┘                  │   │
│   │                          │                              │   │
│   │                    ┌─────┴─────┐                        │   │
│   │                    │   Bridge  │                        │   │
│   │                    │  (cni0)   │                        │   │
│   │                    └─────┬─────┘                        │   │
│   │                          │                              │   │
│   └──────────────────────────┼──────────────────────────────┘   │
│                              │                                   │
│                         To other nodes                           │
│                                                                 │
└────────────────────────────────────────────────────────────────┘
```

Зупиніться й спрогнозуйте: якщо kubelet може запустити пісочницю, але виклик CNI `ADD` зазнає невдачі ще до призначення IP-адреси, яких полів, на вашу думку, бракуватиме у виводі `kubectl get pod -o wide` і логи якого компонента ви оглянете першими? Корисна відповідь — не просто «перевір Под»; це спрогнозувати, чи має Под `PodIP`, чи згадують події kubelet мережевий плагін, і чи справний агент CNI на тій самій ноді. Такий прогноз перетворює велику мережеву проблему на короткий ланцюжок перевірок.

Перший крок інспекції — з'ясувати, який плагін установлено та чи бачить kubelet файл конфігурації CNI. На багатьох кластерах `/opt/cni/bin/` містить виконувані плагіни, а `/etc/cni/net.d/` — упорядковані файли конфігурації або conflist, які використовує середовище виконання контейнерів. Це файли рівня ноди, тож `kubectl` може підказати, який DaemonSet має бути присутній, тоді як прямий доступ до ноди показує, що насправді доступне kubelet.

Ставтеся до файлової системи ноди як до доказу, а не як до запрошення редагувати під час першої реакції. Якщо файл конфігурації відсутній, це вагомий натяк, що плагін ніколи не було встановлено правильно або що завантаження ноди дало збій. Якщо файл існує, але Под'и все одно не запускаються, наступний доказ має надійти з подій kubelet і логів плагіна. Редагування conflist без розуміння того, як оператор плагіна узгоджує його, може призвести до того, що ваша локальна зміна зникне, або до появи ноди, яка більше не відповідає решті кластера.

```bash
# CNI binary location
ls /opt/cni/bin/

# CNI configuration location
ls /etc/cni/net.d/

# Example: View CNI config
cat /etc/cni/net.d/10-calico.conflist
```

```bash
# Check which CNI is installed
ls /etc/cni/net.d/

# Check CNI pods
kubectl get pods -n kube-system | grep -E "calico|flannel|cilium|canal|kindnet"

# Check CNI daemonset
kubectl get daemonset -n kube-system

# View CNI configuration
cat /etc/cni/net.d/*.conf* 2>/dev/null
```

У лабораторіях на kind типовим CNI за замовчуванням є `kindnet`, тож додавайте його до грепів виявлення, перш ніж припускати, що CNI відсутній.

## Вибір плагіна, IPAM та трафік між нодами

Популярні плагіни CNI мають однаковий широкий контракт, але роблять різні компроміси щодо маршрутизації, інкапсуляції, політик, спостережуваності та операційної складності. Flannel навмисно простий і часто використовує VXLAN, щоб швидко запустити мережу Под'ів, але сам по собі не застосовує мережеві політики Kubernetes. Calico може працювати з оверлеями або маршрутизованими дизайнами на BGP і широко використовується там, де важливе застосування політик. Cilium використовує eBPF для мережі, політик, спостережуваності та опційної заміни kube-proxy, що буває потужним, але вимагає від команди розуміння іншої поверхні налагодження.

Ці компроміси — не лише архітектурні рішення платформи; вони визначають команди, якими ви скористаєтесь у поганий день. Кластер Flannel на VXLAN спрямовує вас до тунельних інтерфейсів, оренди підмереж та досяжності між нодами через UDP. Кластер Calico може спрямувати вас до пулів IP, логів Felix, BGP-пірів або трасування політик. Кластер Cilium може спрямувати вас до статусу агента, ідентичності ендпойнтів, мап eBPF та даних потоків Hubble. CKA не вимагає опанування кожного плагіна, але очікує, що ви розпізнаєте: «CNI» — це родина реалізацій, а не одна поведінка.

| Плагін | Мережева політика | Продуктивність | Сценарій використання |
|--------|----------------|-------------|----------|
| **Calico** | Так | Висока | Enterprise, орієнтований на безпеку |
| **Cilium** | Так (розширена) | Дуже висока | eBPF, спостережуваність |
| **Flannel** | Ні | Середня | Прості кластери |
| **Canal** | Так | Середня | Політики Calico + мережа Flannel |
| **AWS VPC CNI** | Через Calico | Висока | Нативний для EKS |

Вибір плагіна — це менше про пошук універсально найкращої площини даних і більше про відповідність вимог операційній зрілості. Апаратний навчальний кластер без вимог до політик може цінувати малу поверхню Flannel. Регульоване середовище, якому потрібна ізоляція просторів імен, зручні для аудиту політики та явні контролі вихідного трафіку, не повинне обирати плагін, який тихо ігнорує мережеві політики. Велика платформна команда може обрати Cilium, бо видимість eBPF і заміна kube-proxy знімають інші вузькі місця, але ця команда також приймає крутішу криву навчання, коли читає мапи BPF, логи агента та прапорці функцій.

Найлегша помилка — обирати під день встановлення, а не під рік експлуатації. Плагін, який просто встановити, може стати дорогим, якщо кожен контроль безпеки доведеться додавати пізніше другим компонентом. Плагін із багатьма розширеними можливостями може стати дорогим, якщо чергова команда не здатна швидко інтерпретувати його вивід про стан здоров'я. Хороший документ дизайну має зазначати, які функції навмисно ввімкнено, які свідомо лишено вимкненими, і які симптоми належать платформній команді, а не власникам застосунків.

Виділення IP — це перше рішення площини даних, що з'являється у повсякденній експлуатації. У кластері в стилі kubeadm CIDR Под'ів кластера може бути `10.244.0.0/16`, а кожна нода може отримати менший CIDR Под'ів, як-от `10.244.1.0/24`. Точна механіка залежить від плагіна й конфігурації контролера, але висновок для налагодження сталий: якщо CIDR Под'ів ноди відсутній, вичерпаний або не збігається з конфігурацією плагіна, нові Под'и на цій ноді дають збій ще до того, як виконається код застосунку.

Збої IPAM часто читають хибно, бо контейнера застосунку може ще не існувати. Об'єкт Под'а існує, планувальник обрав ноду, і kubelet намагався підготувати пісочницю, але крок налаштування мережі зазнав невдачі раніше, ніж запустився контейнер. Саме тому `kubectl logs` може не мати нічого корисного для робочого навантаження. У цьому стані події `kubectl describe pod`, логи kubelet і логи CNI цінніші за діагностику рівня застосунку, бо застосунок ніколи не дійшов до точки, де міг би прив'язатися до порту чи писати логи.

Трафік у межах однієї ноди — найпростіший шлях, бо пакету зазвичай не потрібна фізична мережа. Под A надсилає трафік через свій `eth0`, пакет перетинає veth-пару в простір імен хоста, і міст чи площина даних спрямовують його до veth Под'а B. Якщо цей шлях не працює, тоді як обидва Под'и мають IP на одній ноді, зосередьтеся на локальній площині даних ноди, інтерфейсах Под'ів, таблицях маршрутизації, мережевій політиці чи поведінці брандмауера хоста, перш ніж досліджувати оверлеї.

Саме тому розташування тестів має значення. Якщо ви створите два Под'и без перевірки того, на які ноди вони потрапили, успішний ping може лише довести мережу в межах однієї ноди, а невдалий ping може залучити маршрутизацію між нодами раніше, ніж ви усвідомлюєте. Скористайтеся `kubectl get pods -o wide`, перш ніж тлумачити результат. Для навмисного тестування ви можете застосувати селектори нод, affinity або повторне планування в лабораторії, але важлива звичка — включати розташування на нодах до доказів, які ви занотовуєте.

Трафік між нодами додає мережу нод і модель маршрутизації плагіна. Оверлеї VXLAN загортають пакет Под'а у пакет між нодами, IP-in-IP робить іншу інкапсуляцію, дизайни на BGP оголошують CIDR Под'ів маршрутизаторам чи сусіднім нодам, а хмарні плагіни можуть приєднувати адреси Под'ів безпосередньо до хмарних мережевих конструкцій. Практичний тест — порівняти поведінку в межах однієї ноди й між нодами: якщо в межах однієї ноди працює, а між нодами — ні, пакет, найімовірніше, досягає краю локальної ноди й потім втрачає шлях до CIDR віддаленого Под'а.

Кожна модель маршрутизації створює окремий підпис збою. Збої інкапсуляції часто виглядають як справні Под'и без трафіку між нодами, бо underlay блокує протокол тунелю. Збої BGP часто проявляються відсутніми чи застарілими маршрутами до CIDR віддалених Под'ів. Хмарні збої можуть виглядати як вичерпання адрес, відсутність вторинних адрес або правила груп безпеки, які дозволяють перевірки стану нод, але не трафік між Под'ами. Спільна риса в тому, що виділення IP Под'а вже відбулося, тож наступне питання — чи знають інші ноди, як повернути трафік на цю адресу.

Корисний прогноз — що кожен Под має непорожній IP, що Под'и на різних нодах займають різні CIDR Под'ів нод, і що кожен Под має маршрут за замовчуванням, який вказує на наданий CNI шлюз чи інтерфейс. Коли спостережений вивід порушує цей прогноз, ви можете класифікувати проблему як IPAM, локальне приєднання чи маршрутизацію між нодами замість того, щоб трактувати її як загальний випадок «мережа зламана».

## kube-proxy, Сервіси, DNS та мережа хоста

CNI доставляє пакети між IP Под'ів, але Сервіси Kubernetes додають другу абстракцію: стабільні віртуальні IP та DNS-імена, що вказують на рухливий набір ендпойнтів. kube-proxy стежить за Сервісами та EndpointSlice, а потім програмує локальні правила площини даних ноди так, щоб трафік до ClusterIP досягав одного з IP бекенд-Под'ів. Саме тому Под може дістатися `web.default.svc.cluster.local`, навіть якщо фактичний Под nginx згодом перепланують на іншу ноду.

EndpointSlice — це міст між абстракцією API та площиною даних сервісу. Селектор Сервісу знаходить Под'и, площина управління записує інформацію про ендпойнти, а kube-proxy використовує цю інформацію, щоб оновити правила ноди. Якщо Сервіс не має ендпойнтів, kube-proxy може бути цілком справним і все одно не мати куди корисно надсилати трафік. Саме тому налагодження сервісу завжди має включати селектори та ендпойнти перед правилами пакетів рівня ноди, особливо коли щойно викотили новий Деплоймент.

| Режим | Опис | Продуктивність | Сценарій використання |
|------|-------------|-------------|----------|
| **nftables** | Використовує nftables | Найкраща | Рекомендований сучасний режим (GA з 1.33+, ядро ≥5.13); вмикайте явно |
| **iptables** | Використовує правила iptables | Добра | За замовчуванням у Linux, коли режим не вказано |
| **IPVS** | Використовує IPVS ядра | Краща | Велика кількість Под'ів (має відомі граничні випадки) |
| **userspace** | Застарілий проксі в просторі користувача | Погана | Уникайте; визнано застарілим |

Режим kube-proxy має найбільше значення, коли плинність або кількість сервісів стають великими. Режим iptables лишається типовим у Linux, коли режим не налаштовано явно, тому багато кластерів і лабораторних середовищ досі показують докази iptables. nftables набув статусу GA у Kubernetes 1.33+, рекомендований як сучасний режим, коли ноди працюють на підтримуваному ядрі, як-от Linux 5.13 чи новіше, і його варто вмикати явно після того, як ви підтвердите сумісність. IPVS досі трапляється в старіших високонавантажених кластерах, але має граничні випадки й операційні відмінності, через які nftables є кращою сучасною відповіддю, якщо тільки у вашому середовищі немає конкретної причини обрати інакше.

Для CKA ви навряд чи перепроєктовуватимете режим kube-proxy під час іспиту, але розпізнавання режиму допомагає читати правильні докази. Режим iptables вказує на `iptables-save`, ланцюжки NAT та порядок правил. IPVS вказує на `ipvsadm` та таблиці віртуальних серверів. nftables вказує на набір правил nftables та конфігурацію kube-proxy. Послідовність налагодження вищого рівня лишається тією самою, але команди ноди й очікування щодо продуктивності змінюються разом із режимом.

```
┌────────────────────────────────────────────────────────────────┐
│                   kube-proxy Flow                               │
│                                                                 │
│   Client Pod                                                   │
│       │                                                         │
│       │ Request to Service IP 10.96.45.123:80                  │
│       ▼                                                         │
│   ┌───────────────────────────────────────────────────────┐    │
│   │             kube-proxy dataplane                       │    │
│   │        (iptables / nftables / IPVS)                    │    │
│   │                                                        │    │
│   │  Virtual-IP rule/map:                                 │    │
│   │  10.96.45.123:80 → backend pod IP selection           │    │
│   │                                                        │    │
│   │  Selected: 10.244.1.5:8080                            │    │
│   └───────────────────────────────────────────────────────┘    │
│       │                                                         │
│       ▼                                                         │
│   Backend Pod (10.244.1.5:8080)                                │
│                                                                 │
│   kube-proxy watches API server for Service/Endpoint changes  │
│   and updates service dataplane rules accordingly             │
│                                                                 │
└────────────────────────────────────────────────────────────────┘
```

Коли сервісний трафік дає збій, відокремте розрізнення імен від маршрутизації віртуального IP. Под, який не може розрізнити `web`, може мати проблему з конфігурацією CoreDNS чи резолвера. Под, який розрізняє `web` у ClusterIP, але не може під'єднатися, може не мати ендпойнтів, мати заблоковану мережеву політику, збій kube-proxy чи проблеми бекенд-застосунку. Под, який може дістатися IP бекенд-Под'а напряму, але не ClusterIP, вказує радше на kube-proxy чи правила площини даних сервісу, ніж на маршрутизацію CNI між нодами.

Цей поділ запобігає поширеному хибному висновку: «DNS зламано» щоразу, коли URL дає збій. `wget http://web` включає пошук імені, маршрутизацію віртуального IP сервісу, вибір бекенда, мережеву політику та відповідь застосунку. Заміна цього єдиного тесту на `nslookup web`, `kubectl get endpointslice`, прямий доступ за IP Под'а та доступ за ClusterIP дає вам ланцюжок фактів. Перша порвана ланка в цьому ланцюжку — це місце, де належить наступна детальна інспекція.

```bash
# Check kube-proxy pods
kubectl get pods -n kube-system -l k8s-app=kube-proxy

# Check kube-proxy mode from configuration first
kubectl get configmap kube-proxy -n kube-system -o yaml | grep -A2 '^[[:space:]]*mode:'

# Recent logs can confirm the proxier that started
kubectl logs -n kube-system -l k8s-app=kube-proxy --tail=20 | grep -iE 'Using|Proxier|mode'

# View kube-proxy configmap
kubectl get configmap kube-proxy -n kube-system -o yaml

# Check iptables rules (on node)
iptables -t nat -L KUBE-SERVICES -n | head -20

# Check IPVS rules (if using IPVS mode, on node)
ipvsadm -Ln
```

Мережа хоста — це винятковий шлях, що обходить значну частину ізоляції Под'а. З `hostNetwork: true` Под використовує мережевий простір імен ноди, бачить інтерфейси ноди й конкурує за ті самі прослуховувані порти, що й процеси хоста та інші Под'и з мережею хоста на цій ноді. Це доречно для деяких агентів ноди, компонентів CNI та низькорівневої діагностики, але до цього варто ставитися як до привілейованого вибору дизайну, а не як до швидкого виправлення зламаної мережі Под'ів.

Операційна ціна — не лише конфлікт портів. Про Под'и з мережею хоста складніше міркувати, бо їхній трафік може дотримуватися правил брандмауера ноди, конфігурації резолвера ноди й припущень про ідентичність ноди замість звичайної поведінки Под'а. Інструменти моніторингу й політик також можуть звітувати про них інакше. Якщо робочому навантаженню потрібно спостерігати чи змінювати мережу ноди, мережа хоста може бути правильним рішенням; якщо ж робочому навантаженню просто треба бути досяжним, Сервіс, дизайн DaemonSet чи належне відновлення CNI зазвичай безпечніші.

```yaml
# Pod using host network
apiVersion: v1
kind: Pod
metadata:
  name: host-network-pod
spec:
  hostNetwork: true         # Uses node's network namespace
  containers:
  - name: nginx
    image: nginx
    ports:
    - containerPort: 80     # Binds to node's port 80!
```

`hostPort` вужчий: Под усе ще має власний мережевий простір імен, але нода відображає конкретний порт на контейнер. Обидві функції створюють обмеження планування, бо два Под'и не можуть прив'язатися до одного порту хоста на одній ноді. Деталь про DNS легко проґавити: Под'и з мережею хоста зазвичай мають встановлювати `dnsPolicy: ClusterFirstWithHostNet`, інакше вони можуть успадкувати поведінку резолвера ноди й не зможуть розрізнити імена сервісів кластера, тоді як зовнішні імена працюватимуть.

```yaml
# Pod with host port mapping
apiVersion: v1
kind: Pod
metadata:
  name: hostport-pod
spec:
  containers:
  - name: nginx
    image: nginx
    ports:
    - containerPort: 8080
      hostPort: 80           # Node's port 80 → container 8080
```

Зупиніться й спрогнозуйте: ви встановлюєте `hostNetwork: true` на Под, що запускає nginx на порту 80, і на тій самій ноді вже є інший Под із мережею хоста, який слухає порт 80. Планувальник може намагатися уникати неможливого розміщення портів хоста, коли порти оголошено, але якщо конфлікт процесів усе одно стається під час виконання, контейнер не може прив'язатися до адреси, і збій виглядатиме як проблема запуску застосунку. Мережевий урок у тому, що мережа хоста змінює одиницю володіння портом з «Под'а» на «ноду».

## Конфігурація CIDR і реальність мережевих політик

CIDR Под'ів, CIDR сервісів і CIDR Под'ів нод — це окремі концепції планування адрес, які не повинні перетинатися. CIDR Под'ів — це адресний простір, призначений Под'ам, CIDR сервісів — віртуальний адресний простір, призначений ClusterIP, а кожна нода може отримати менший CIDR Под'ів для локального виділення. Якщо ви зміните один бік цього плану після створення кластера, вам потрібно розуміти, які контролери, конфігурація CNI та наявні об'єкти все ще покладаються на старий діапазон.

Планування адрес також впливає на майбутнє масштабування. Малий CIDR Под'ів може працювати в лабораторії з двома нодами й жменькою Под'ів, а потім стати жорсткою стелею, коли кожній ноді потрібні сотні адрес Под'ів або платформа розширюється на кілька середовищ. CIDR сервісів, що перетинається з корпоративною маршрутизацією, може створити заплутані збої, коли деякі клієнти надсилають трафік за межі кластера замість віртуальних адрес сервісів. Найбезпечніший час знайти ці конфлікти — до створення кластера, а не під час продакшн-міграції.

| Тип CIDR | Опис | Приклад |
|-----------|-------------|---------|
| **CIDR Под'ів** | Діапазон IP для всіх Под'ів | 10.244.0.0/16 |
| **CIDR сервісів** | Діапазон IP для сервісів | 10.96.0.0/12 |
| **CIDR ноди** | Діапазон Под'ів на ноду | 10.244.1.0/24 |

Невідповідності CIDR створюють збої, що виглядають непов'язаними, доки ви не оглянете шлях виділення. Кластер може ініціалізуватися з `--pod-network-cidr=10.244.0.0/16`, тоді як маніфест плагіна очікує інший пул; Под'и тоді не отримують адреси, отримують адресу, яку інші ноди не маршрутизують, або створюють трафік, що зникає на межі ноди. На CKA ви радше діагностуватимете невідповідність, ніж перепроєктовуватимете весь план адрес, тож навчіться, де читати погляди кластера й плагіна на світ.

Погляд плагіна може жити не в тому самому місці для кожного CNI. Деякі плагіни зберігають пули IP у власних ресурсах, деякі використовують ConfigMap, а хмарні плагіни можуть залежати від хмарних API чи анотацій нод. Саме через цю варіативність перше питання — «який це CNI?», а не «який файл мені редагувати?». Щойно ви ідентифікуєте плагін, користуйтеся його задокументованою поверхнею керування й порівнюйте її з доказами CIDR Под'ів нод у Kubernetes.

```bash
# Check pod CIDR (from kube-controller-manager)
kubectl get cm kubeadm-config -n kube-system -o yaml | grep -i cidr

# Check from nodes
kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.podCIDR}{"\n"}{end}'

# Check service CIDR
kubectl cluster-info dump | grep -m 1 service-cluster-ip-range
```

```bash
# During cluster init
kubeadm init --pod-network-cidr=10.244.0.0/16 --service-cidr=10.96.0.0/12

# The CNI plugin must match this CIDR
# Example: Calico installation with matching CIDR
```

Мережева політика — ще одне місце, де прийняття об'єкта API Kubernetes не гарантує застосування у площині даних. API-сервер може зберегти валідний об'єкт NetworkPolicy, навіть якщо встановлений CNI не реалізує політик. У кластері лише з Flannel це означає, що YAML може виглядати ідеально, а ізоляція все одно бути відсутньою. У кластері Calico чи Cilium застосування також залежить від селекторів, просторів імен, посту default-deny та того, чи є тестований трафік вхідним (ingress), вихідним (egress) чи обома.

Налагодження політик слід розглядати як проблему вибору перед тим, як воно стане проблемою пакетів. Чи обирає політика ті Под'и, що ви думаєте? Чи обирає вона простір імен, з якого ви тестуєте? Чи політика лише ingress, тоді як вимога, що дає збій, — egress? Ви тестуєте трафік до IP Под'а, IP сервісу чи зовнішньої адреси? Письмові відповіді на ці питання часто викривають хибу ще до того, як вам знадобляться глибші специфічні для плагіна інструменти.

Сценарій вправи: власник простору імен створює політику default-deny для вхідного трафіку, а потім дозволяє лише `app=frontend` дістатися `app=api`, але тести з непов'язаного простору імен усе одно проходять. Правильний перший крок — не сліпо переписувати політику; спершу підтвердьте, що плагін підтримує NetworkPolicy, потім підтвердьте, що мітки тестового Под'а й мітки простору імен відповідають селекторам політики, і нарешті протестуйте прямий трафік за IP Под'а та сервісний трафік окремо. Такий порядок запобігає поширеній помилці налагодження YAML, тоді як установлений плагін неспроможний його застосувати.

## Робочий процес налагодження та розібраний приклад

Хороше дослідження мережі рухається від найближчого спостережуваного симптому назовні. Почніть із фази Под'а, подій, IP Под'а та розташування на ноді, потім протестуйте зв'язність за IP Под'а в межах однієї ноди, зв'язність за IP Под'а між нодами, зв'язність до ClusterIP сервісу та DNS. Кожен крок створено, щоб відповісти на одне питання й виключити один рівень. Якщо ви одразу перейдете до зміни маніфестів CNI, ви легко перетворите однонодовий збій на загальнокластерну аварію.

Робочий процес — це ще й інструмент комунікації. Коли ви передаєте інцидент, «мережа зламана» майже марне, але «Под'и на ноді A мають IP, ping у межах однієї ноди працює, трафік за IP Под'а між нодами з ноди A на ноду B дає збій, а тести сервісів kube-proxy не було досягнуто» дає наступному інженеру точну стартову точку. Такий стиль звітування зменшує повторну роботу й захищає кластер від спекулятивних змін. Це та сама дисципліна, яку варто застосовувати у письмових нотатках на іспиті.

```
Pod Network Issue?
    │
    ├── kubectl get pod -o wide (check pod IP, node)
    │
    ├── Pod has IP?
    │   ├── No → CNI issue
    │   │        Check: CNI pods, /etc/cni/net.d/, CNI logs
    │   │
    │   └── Yes → Continue
    │
    ├── Can reach other pods on same node?
    │   ├── No → Bridge/veth issue
    │   │
    │   └── Yes → Continue
    │
    ├── Can reach pods on other nodes?
    │   ├── No → Overlay/routing issue
    │   │        Check: CNI config, node routes, firewall
    │   │
    │   └── Yes → Continue
    │
    ├── Can reach services?
    │   ├── No → kube-proxy or DNS issue
    │   │        Check: kube-proxy mode (iptables/nftables/IPVS), CoreDNS
    │   │
    │   └── Yes → Network is fine, check app
    │
    └── Check NetworkPolicy
        kubectl get networkpolicy
```

Використовуйте команди, що розкривають стан, а не команди, що просто повторюють запит із збоєм. `ip addr` показує, чи має Под очікуваний інтерфейс та адресу, `ip route` показує, як Под надсилає трафік зі свого простору імен, а `/etc/resolv.conf` показує, чи налаштований Под використовувати DNS кластера. З боку площини управління логи DaemonSet CNI, логи kube-proxy та логи CoreDNS допомагають вирішити, чи належить збій до приєднання, маршрутизації сервісу чи розрізнення імен.

Надавайте перевагу коротким парним тестам, а не широким викидам команд. Наприклад, порівняйте `kubectl exec pod1 -- ping <pod-ip>` із `kubectl exec pod1 -- wget --spider http://service-name`, а потім поясніть, що змінилося між цими двома шляхами. Якщо дає збій лише другий, ви додали DNS, маршрутизацію сервісу, вибір бекенда чи поведінку протоколу застосунку. Якщо обидва дають збій, проблема, ймовірно, нижче по шляху. Цей метод тримає дослідження зрозумілим навіть тоді, коли в кластері багато рухомих частин.

```bash
# Check pod network
kubectl exec <pod> -- ip addr
kubectl exec <pod> -- ip route
kubectl exec <pod> -- cat /etc/resolv.conf

# Test connectivity
kubectl exec <pod> -- ping <other-pod-ip>
kubectl exec <pod> -- nc -zv <service> <port>
kubectl exec <pod> -- wget --spider --timeout=1 http://<service>

# Check CNI pods
kubectl get pods -n kube-system | grep -E "calico|flannel|cilium|canal|kindnet"
kubectl logs -n kube-system <cni-pod>

# Check kube-proxy
kubectl get pods -n kube-system -l k8s-app=kube-proxy
kubectl logs -n kube-system -l k8s-app=kube-proxy

# Check CoreDNS
kubectl get pods -n kube-system -l k8s-app=kube-dns
kubectl logs -n kube-system -l k8s-app=kube-dns
```

| Симптом | Причина | Розв'язання |
|---------|-------|----------|
| Под застряг у ContainerCreating | CNI не встановлено або він дає збій | Установити/виправити плагін CNI |
| Под не має IP | IPAM вичерпано або помилка CNI | Перевірити логи CNI, розширити CIDR |
| Не вдається дістатися Под'ів на інших нодах | Оверлей неправильно налаштовано | Перевірити мережеву конфігурацію CNI |
| Сервіси недосяжні | kube-proxy не працює | Перевірити Под'и kube-proxy |
| DNS не працює | CoreDNS не працює | Перевірити Под'и CoreDNS |
| Мережева політика не працює | CNI її не підтримує | Використати Calico чи Cilium |

Розібраний приклад: припустімо, `pod1` може пінгувати `pod2`, коли обидва працюють на одній ноді, але ping дає збій після того, як `pod2` перепланують на іншу ноду. Цей результат доводить, що IPAM та локальні інтерфейси Под'а працюють, і робить пояснення через суто сервіс чи DNS малоймовірним, бо ви тестуєте IP Под'ів напряму. Наступні перевірки — це агенти CNI на обох нодах, маршрути ноди до CIDR віддаленого Под'а, оверлейні інтерфейси, як-от `flannel.1` чи `tunl0`, та будь-які правила брандмауера чи груп безпеки, що блокують інкапсуляцію або BGP між нодами.

Тепер припустімо, ті самі два Под'и можуть пінгувати одне одного за IP, але `wget http://web` дає збій після того, як ви створюєте Сервіс для сервера. Дослідження рухається вгору, бо маршрутизація Под'ів уже пройшла. Перевірте, що селектор Сервісу відповідає міткам Под'а, що EndpointSlice містять адресу бекенда, і що kube-proxy справний на ноді клієнта. Якщо Сервіс має ендпойнти й kube-proxy справний, тоді поведінка політики чи застосунку, що слухає порт, стає правдоподібнішою за приєднання CNI.

Зупиніться й подумайте: новий Под застряг у `ContainerCreating`, а події кажуть «network plugin is not ready». Перш ніж змінювати будь-яку конфігурацію CNI, перевірте, чи працює Под DaemonSet CNI на цій ноді, чи містить `/etc/cni/net.d/` файл конфігурації, і чи можуть інші ноди успішно створювати Под'и. Ці три спостереження відрізняють загальнокластерну відсутність встановлення від збою агента, специфічного для ноди, що визначає, чи буде вашою наступною дією встановлення, інспекція логів, відновлення ноди чи очищення ємності.

## Патерни та антипатерни

Найсильніший патерн експлуатації CNI — налагоджувати порівнево й зупинятися, коли докази змінюють рівень. Под без IP — це проблема приєднання чи IPAM. Под з IP, який не може дістатися сусіда на одній ноді, — це проблема локальної площини даних чи політики. Под, який може дістатися IP сусідніх Под'ів, але не ClusterIP, найімовірніше залучає kube-proxy, ендпойнти чи правила сервісу. Ця дисципліна тримає дослідження достатньо малим, щоб завершити його під тиском іспиту, і достатньо безпечним для налагодження в продакшні.

Інший корисний патерн — тримати в кожному кластері напоготові завідомо справний мережевий зонд. Крихітний Под у стилі BusyBox чи netshoot може надати `ip`, `route`, `nslookup`, `wget` та `nc`, не змінюючи образи застосунків. У заблокованих продакшн-середовищах зонд має бути контрольованим і підлягати аудиту, але принцип лишається цінним: вам потрібен нейтральний клієнт, чия поведінка не переплетена із застосунком, який ви діагностуєте.

| Патерн | Коли застосовувати | Чому працює | Міркування щодо масштабування |
|---------|-------------|--------------|-----------------------|
| Порівневі тести зв'язності | Будь-який інцидент Под'а, сервісу чи DNS | Кожен тест ізолює поведінку CNI, kube-proxy, CoreDNS чи застосунку | Автоматизуйте послідовність у runbook'ах, щоб команди збирали зіставні докази |
| CNI з підтримкою політик за замовчуванням | Кластери з ізоляцією просторів імен чи вимогами відповідності | Мережеву політику можна застосувати, лише коли площина даних її реалізує | Плануйте впровадження default-deny поступово, щоб не блокувати спільні сервіси |
| Планування CIDR до створення кластера | Нові кластери, перебудови лабораторій чи міграції платформи | Діапазони Под'ів і сервісів важко чисто змінити після появи навантажень | Зарезервуйте достатньо адресного простору для зростання нод, планів dual-stack та тестових кластерів |
| Збір доказів локально на ноді | Збої, ізольовані на одній ноді | Файли конфігурації CNI, маршрути та стан агента специфічні для ноди | Тримайте доступ до нод під аудитом і надавайте перевагу командам лише для читання під час тріажу |

Найпоширеніший антипатерн — ставитися до CNI як до чорної скриньки, доки щось не зламається. Команди встановлюють плагін один раз, забувають, який режим він використовує, а потім припускають, що кожен мережевий симптом — це проблема застосунку. Кращий підхід — записати плагін, підтримку політик, режим інкапсуляції чи маршрутизації, CIDR Под'ів, CIDR сервісів та режим kube-proxy як частину документації кластера. Цей запис прискорює інциденти, бо перший відповідач починає з фактичного дизайну, а не перевідкриває його під час збою.

Будьте обережні з «виправленнями», що працюють шляхом обходу моделі. Додавання `hostNetwork: true`, відкриття більшої кількості NodePort'ів чи дозвіл усього трафіку в мережевій політиці можуть зробити один тест успішним, водночас послаблюючи дизайн кластера. До таких змін слід ставитися як до тимчасових експериментів, якщо тільки вони не відповідають вимогам робочого навантаження. Краща альтернатива — визначити, який рівень дав збій, і відновити задуманий контракт: Под'и отримують маршрутизовані IP, сервіси маршрутизують до ендпойнтів, DNS розрізняє імена сервісів, а політики виражають навмисний доступ.

| Антипатерн | Що йде не так | Краща альтернатива |
|--------------|-----------------|--------------------|
| Встановити Flannel і вважати, що політики працюють | Об'єкти NetworkPolicy приймаються, але не застосовуються | Обрати Calico, Cilium, Canal чи інший дизайн з підтримкою політик |
| Змінювати CIDR Под'ів після появи навантажень | Наявні маршрути, пули та виділення нод розходяться | Перебудувати чи мігрувати навмисно із задокументованим плануванням адрес |
| Налагоджувати DNS сервісу перед зв'язністю за IP Под'а | Розрізнення імен ховає збої CNI нижчого рівня | Спершу довести зв'язність за IP Под'а, потім за IP сервісу, потім DNS |
| Використовувати мережу хоста як обхідний шлях | Под'и втрачають звичайну мережеву ізоляцію та конкурують за порти ноди | Виправити шлях CNI, якщо тільки навантаженню справді не потрібен доступ до простору імен хоста |
| Прочитати один справний Под CNI й оголосити успіх | Стан здоров'я DaemonSet може різнитися на нодах | Перевірити розташування на нодах, логи ураженої ноди та файли конфігурації для кожної ноди |

## Фреймворк прийняття рішень

Коли ви обираєте чи налагоджуєте шлях CNI, поставте три питання по порядку: яка гарантія мені потрібна, де спостережено збій, і який компонент володіє цим рівнем? Для нового кластера «яка гарантія» включає застосування мережевих політик, хмарну інтеграцію, спостережуваність, апаратну маршрутизацію та обізнаність команди. Для інциденту «де спостережено» означає створення Под'а, зв'язність за IP Под'а, зв'язність за IP сервісу, DNS чи поведінку політики. Питання про власника потім вказує на CNI, kube-proxy, CoreDNS, застосунок чи мережу ноди в основі.

Цей фреймворк тримає дизайн і налагодження пов'язаними. Якщо ваш дизайн вимагає застосованої ізоляції орендарів, власник — не лише автор YAML; це площина даних CNI, яка має застосувати політику. Якщо ваш симптом — затримка оновлення сервісу, власник, імовірно, режим kube-proxy чи замінна площина даних, а не IPAM. Якщо ваш симптом — збій створення Под'а, специфічний для ноди, власником може бути агент CNI на цій ноді. Та сама мапа власників допомагає обрати правильну документацію й правильні логи.

```
Choose or debug CNI path
    │
    ├── Need Kubernetes NetworkPolicy?
    │   ├── Yes → Choose policy-capable CNI (Calico, Cilium, Canal, cloud + policy)
    │   └── No  → Simpler CNI may be acceptable for labs or low-risk clusters
    │
    ├── Pod has no IP?
    │   ├── Yes → Inspect CNI install, IPAM, node CNI config, kubelet events
    │   └── No  → Continue to connectivity tests
    │
    ├── Pod IP works but Service IP fails?
    │   ├── Yes → Inspect endpoints, kube-proxy mode, service rules, backend readiness
    │   └── No  → Continue to DNS and policy checks
    │
    └── DNS name fails but ClusterIP works?
        ├── Yes → Inspect CoreDNS, resolver config, hostNetwork dnsPolicy
        └── No  → Re-check application listener, policy, and routes
```

| Вимога чи симптом | Надавайте перевагу цьому напрямку | Уникайте цього напрямку |
|------------------------|-----------------------|----------------------|
| Потрібен простий навчальний кластер | Flannel чи типовий лабораторний CNI | Надбудова функцій, які команда не може експлуатувати |
| Потрібна ізоляція просторів імен | Calico, Cilium, Canal чи хмарне налаштування з підтримкою політик | Лише Flannel із незастосованими політиками |
| Потрібна глибока видимість потоків | Cilium чи плагін із сильним інструментарієм спостережуваності | Мінімальний плагін без корисної діагностики рівня ноди |
| Створення Под'а дає збій до призначення IP | Встановлення CNI, IPAM, файли конфігурації, логи агента ноди | kube-proxy і CoreDNS спершу |
| ClusterIP дає збій, тоді як IP Под'а працює | kube-proxy, ендпойнти, селектор сервісу, готовність бекенда | Перевстановлення CNI без доказів |
| Под із мережею хоста не може розрізнити сервіси | `dnsPolicy: ClusterFirstWithHostNet` та інспекція резолвера | Припущення, що успіх зовнішнього DNS доводить роботу DNS кластера |

Який підхід ви б обрали тут і чому: малому апаратному кластеру потрібне застосування мережевих політик, команда впевнено почувається з Kubernetes, але не з BGP, а служба безпеки хоче ізоляцію default-deny на рівні простору імен протягом першого місяця? Розумна відповідь — обрати плагін із підтримкою політик з оверлеєм чи простим режимом маршрутизації, задокументувати впровадження політик і уникати дизайну, насиченого BGP, доки команда не зможе його експлуатувати. Суть — пов'язати вибір плагіна з вимогами та операційними навичками, а не ранжувати плагіни за популярністю.

Для рішень щодо міграції додайте ще одне питання: чи можете ви витримати перебудову нод чи кластерів? Зміни CNI можуть вплинути на адреси Под'ів, семантику політик, маршрути нод та припущення площини даних сервісу. Деякі міграції можливі на місці з настановами постачальника, тоді як інші безпечніші як blue-green міграції кластерів. На іспиті ви не виконуватимете складну міграцію, але в реальній платформній роботі саме цей ризик пояснює, чому вибір CNI заслуговує на раннє проєктне увагу.

## Чи знали ви?

- **CNI передує багатьом мережевим зручностям Kubernetes**: специфікація CNI визначає контракт між середовищем виконання та плагіном з операціями на кшталт `ADD` і `DEL`, тому kubelet може покладатися на різні плагіни, не вшиваючи одну мережеву реалізацію.

- **Kubernetes не постачає мережі Под'ів за замовчуванням**: після `kubeadm init` вам усе ще потрібно встановити сумісний плагін CNI, перш ніж звичайні Под'и та CoreDNS зможуть стати корисними.

- **Сам по собі Flannel не застосовує мережевих політик**: NetworkPolicy — це API Kubernetes, але застосування делеговано мережевій реалізації, тож непідтримувані плагіни можуть лишати валідні об'єкти політик без ефекту в площині даних.

- **nftables — сучасний режим kube-proxy, який варто оцінити**: iptables лишається типовим у Linux, коли режим kube-proxy не вказано, але nftables набув статусу GA й рекомендований для сучасних кластерів, коли ноди працюють на підтримуваному ядрі, тож кластери Kubernetes 1.35 мають явно оцінити його, перш ніж обирати IPVS чи лишатися на iptables.

## Типові помилки

| Помилка | Чому стається | Як виправити |
|---------|----------------|---------------|
| Встановити Kubernetes і забути про CNI | kubeadm створює компоненти площини управління, тож кластер виглядає частково живим до того, як запрацює мережа Под'ів | Встановити сумісний плагін CNI і підтвердити наявність Под'ів CNI та `/etc/cni/net.d/` |
| Використовувати Flannel, покладаючись на NetworkPolicy | API-сервер приймає об'єкти політик, навіть коли плагін їх не застосовує | Обрати Calico, Cilium, Canal чи іншу реалізацію з підтримкою політик |
| Змішувати CIDR Под'ів між kubeadm і плагіном | Контролер кластера й плагін виділяють чи маршрутизують різні діапазони адрес | Узгодити `--pod-network-cidr`, пули IP плагіна та CIDR Под'ів нод до створення навантажень |
| Налагоджувати DNS перед перевіркою зв'язності за IP Под'а | Імена сервісів дають збій з багатьох причин, зокрема через збої мережі Под'ів нижчого рівня | Протестувати IP Под'а, потім ClusterIP, потім DNS і записати, яка межа першою дала збій |
| Забути `ClusterFirstWithHostNet` на Под'ах із мережею хоста | Под'и з мережею хоста можуть успадкувати поведінку резолвера ноди замість DNS кластера | Встановити `dnsPolicy: ClusterFirstWithHostNet`, коли Под'ам із мережею хоста потрібне виявлення сервісів |
| Вважати, що один справний Под CNI доводить справність усіх нод | CNI працює як DaemonSet, і один збійний агент ноди може зламати лише ті Под'и, що розміщені на ній | Перевірити `kubectl get pods -n kube-system -o wide` і порівняти ноди ураженого навантаження |
| Перевстановлювати CNI під час кожного мережевого інциденту | Мережеві симптоми можуть належати kube-proxy, ендпойнтам, DNS, NetworkPolicy чи застосунку | Використовувати порівневий робочий процес і змінювати компонент-власник лише після того, як докази вкажуть туди |

## Тест

<details>
<summary>Питання 1: Після `kubeadm init` CoreDNS і Под'и застосунків лишаються у стані `ContainerCreating`, а події згадують, що мережевий плагін не готовий. Яка найімовірніша корінна причина і що варто перевірити перед розгортанням навантажень?</summary>

Найімовірніша причина — не встановлено робочого плагіна CNI або kubelet не може прочитати валідну конфігурацію CNI на ноді. Kubernetes може створювати основні об'єкти площини управління, не надаючи мережі Под'ів, тож CoreDNS уражений, бо сам є Под'ом. Перевірте, що DaemonSet CNI працює, що `/etc/cni/net.d/` містить очікувану конфігурацію, і що CIDR плагіна відповідає CIDR Под'ів кластера. Не налагоджуйте CoreDNS першим, бо DNS залежить від готовності мережі Под'ів.
</details>

<details>
<summary>Питання 2: Ваша команда використовує Flannel і створює NetworkPolicies для ізоляції продакшну, але трафік між просторами імен усе одно проходить. Селектори політик правильні. Що дало збій у дизайні?</summary>

Дизайн припускає, що застосування NetworkPolicy виконує сам Kubernetes, але застосування належить мережевій реалізації. Сам по собі Flannel надає мережу Под'ів, але не застосовує NetworkPolicy, тож об'єкти API можуть існувати без зміни поведінки трафіку. Виправлення — використати плагін із підтримкою політик, як-от Calico чи Cilium, або комбінований підхід на кшталт Canal, коли це доречно. Переписування тих самих селекторів не вирішить проблему, бо площині даних бракує функції застосування.
</details>

<details>
<summary>Питання 3: Под'и на одній ноді можуть пінгувати одне одного за IP Под'а, але Под'и на різних нодах — ні. Обидва Под'и мають IP-адреси, і обидві ноди у стані Ready. Який рівень слід дослідити наступним?</summary>

Це вказує радше на маршрутизацію CNI між нодами чи інкапсуляцію, ніж на базове створення Под'а. Успіх у межах однієї ноди доводить, що шлях через локальний veth і міст чи локальну площину даних працює, тоді як збій між нодами додає рівень мережі нод, оверлею, BGP чи хмарної маршрутизації. Перевірте агенти CNI на обох нодах, маршрути до CIDR віддалених Под'ів, оверлейні інтерфейси та правила брандмауера для протоколу плагіна між нодами. kube-proxy — не перший підозрюваний, бо тест використовує IP Под'ів, а не ClusterIP Сервісів.
</details>

<details>
<summary>Питання 4: Под може під'єднатися напряму до IP бекенд-Под'а, але з'єднання з ClusterIP Сервісу завершується таймаутом. Розрізнення DNS повертає очікуваний ClusterIP. Що слід перевірити перед зміною CNI?</summary>

Прямий тест за IP Под'а підказує, що зв'язність CNI між Под'ами для цього шляху працює, а успішне розрізнення DNS означає, що CoreDNS повернув адресу сервісу. Лишається рівень маршрутизації сервісу й вибору бекенда, тож перевірте селектор Сервісу, EndpointSlice чи Endpoints, готовність бекенда та справність чи режим kube-proxy. Також розумно оглянути локальні правила сервісу на ноді, якщо у вас є доступ до неї. Перевстановлення CNI було б передчасним, бо докази вказують на шлях віртуального IP.
</details>

<details>
<summary>Питання 5: Под із мережею хоста може розрізнити публічні домени, але не може розрізнити `kubernetes.default.svc`. Яка однорядкова зміна специфікації Под'а зазвичай потрібна і чому?</summary>

Встановіть `dnsPolicy: ClusterFirstWithHostNet` на Под. Под із мережею хоста використовує мережевий простір імен ноди, і без цієї спеціальної політики DNS він може успадкувати налаштування резолвера, що вказують на інфраструктурний DNS замість CoreDNS. Публічний DNS усе ще може працювати, бо резолвер ноди знає зовнішні домени, що робить симптом оманливим. Ця політика каже kubelet налаштувати поведінку DNS кластера, навіть якщо Под використовує мережу хоста.
</details>

<details>
<summary>Питання 6: У вашому кластері тисячі Сервісів, CPU kube-proxy стрибає під час оновлень Сервісів, а кластер досі використовує режим iptables. Який напрямок варто оцінити для Kubernetes 1.35?</summary>

Оцініть спершу режим nftables, бо це сучасний напрямок kube-proxy, спроєктований обробляти правила сервісів ефективніше за застарілу поведінку iptables. IPVS теж може траплятися в старіших високонавантажених дизайнах, але має власні граничні випадки й більше не є типовою рекомендацією для нових кластерів. Заміна kube-proxy від Cilium може бути слушним вибором платформи, коли команда вже експлуатує Cilium. Важливе міркування в тому, що вартість оновлення сервісів належить kube-proxy чи дизайну площини даних сервісу, а не виділенню IP Под'ів.
</details>

<details>
<summary>Питання 7: Нода більше не може запускати нові Под'и, але інші ноди продовжують успішно планувати Под'и. Збійні Под'и не мають IP Под'а. Який доказ відрізняє локальний для ноди збій CNI від загальнокластерної проблеми дизайну CIDR?</summary>

Порівняйте уражену ноду зі справною, а не дивіться лише на один збійний Под. Якщо інші ноди досі виділяють IP Под'ів, CIDR кластера, ймовірно, не вичерпано глобально, а збійна нода може мати відсутній файл конфігурації CNI, аварійний агент CNI, невалідний локальний стан чи вичерпане локальне виділення ноди. Перевірте розташування DaemonSet CNI, події ноди, `/etc/cni/net.d/` та логи плагіна на ураженій ноді. Глобальна невідповідність CIDR зазвичай уражає нові Под'и по всьому кластеру, особливо після свіжого встановлення.
</details>

## Практична вправа

Сценарій вправи: вам надано кластер Kubernetes 1.35 і просять довести, що мережа Под'ів, маршрутизація сервісів, DNS та поведінка мережі хоста достатньо справні для команд застосунків. Пройдіть завдання по порядку й занотовуйте перший рівень, що дає збій, якщо ваше середовище поводиться інакше. Мета — не запам'ятати вивід; мета — відпрацювати повторюваний шлях інспекції, який ви зможете використати під час CKA та в реальній експлуатації.

### Завдання 1: Ідентифікувати встановлений CNI

Почніть із виявлення плагіна як з API Kubernetes, так і з файлової системи ноди. Погляд API підказує, які агенти нод мають існувати, а погляд файлової системи показує, чи має kubelet конфігурацію CNI для виклику. Якщо у вашій лабораторії немає доступу до оболонки ноди, зафіксуйте це обмеження й покладайтеся на логи DaemonSet та Под'ів для доказів із боку Kubernetes.

```bash
# Check CNI pods
kubectl get pods -n kube-system | grep -E "calico|flannel|cilium|canal|kindnet|cni"

# Check CNI daemonsets
kubectl get ds -n kube-system

# Check CNI configuration on a node
ls /etc/cni/net.d/ 2>/dev/null || echo "Run on a node with shell access"
```

<details>
<summary>Настанови до розв'язання</summary>

Справний кластер має показувати один агент ноди CNI на кожну планувальну ноду, зазвичай через DaemonSet у `kube-system`. Якщо Под'и CNI не з'являються, а `/etc/cni/net.d/` порожній, кластер, імовірно, не може під'єднувати звичайні Под'и до мережі. Якщо Под'и CNI існують, але створення навантажень дає збій лише на одній ноді, порівняйте Под і файли конфігурації CNI на цій конкретній ноді зі справною нодою.
</details>

### Завдання 2: Оглянути CIDR Под'ів і сервісів

Далі огляньте діапазони адрес, які площина управління й ноди вважають за потрібне використовувати. CIDR Под'ів і CIDR сервісів мають бути окремими, а плагін має узгоджуватися з діапазоном Под'ів, який він має виділяти чи маршрутизувати. Запишіть CIDR Под'ів нод, бо вони полегшують міркування про проблеми маршрутизації між нодами згодом.

```bash
# Get node CIDRs
kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.name}{": "}{.spec.podCIDR}{"\n"}{end}'

# Check pod CIDR from kubeadm config if available
kubectl get cm kubeadm-config -n kube-system -o yaml 2>/dev/null | grep -i cidr

# Check service CIDR from cluster dump if available
kubectl cluster-info dump | grep -m 1 service-cluster-ip-range
```

<details>
<summary>Настанови до розв'язання</summary>

Ви маєте побачити CIDR Под'ів на ноду в багатьох кластерах у стилі kubeadm, хоча деякі дизайни CNI та хмарні дизайни представляють виділення інакше. Відсутній чи несподіваний CIDR Под'ів ноди — це натяк, а не остаточний діагноз. Підтвердьте дизайн плагіна, перш ніж припускати, що кожен кластер мусить показувати точно ті самі поля.
</details>

### Завдання 3: Створити тестові Под'и й оглянути їхній мережевий погляд

Створіть два тимчасові Под'и й огляньте їхні IP-адреси, маршрути та конфігурацію резолвера. Це дає вам завідому пару клієнт-сервер для подальших тестів. Якщо Под'и не стають готовими, не переходьте до тестування сервісів; огляньте події та логи CNI, бо рівень приєднання вже дав збій.

```bash
kubectl run pod1 --image=busybox:1.36 --command -- sleep 3600
kubectl run pod2 --image=busybox:1.36 --command -- sleep 3600

# Wait for ready
kubectl wait --for=condition=ready pod/pod1 pod/pod2 --timeout=60s

# Get pod IPs and node placement
kubectl get pods -o wide

# Check pod network interface and routes
kubectl exec pod1 -- ip addr
kubectl exec pod1 -- ip route

# Check DNS configuration
kubectl exec pod1 -- cat /etc/resolv.conf
```

<details>
<summary>Настанови до розв'язання</summary>

Обидва Под'и мають мати IP Под'ів, а `pod1` має показувати інтерфейс і конфігурацію маршрутів, встановлені CNI. Конфігурація резолвера має включати поведінку DNS кластера для звичайних Под'ів. Якщо `pod1` не має IP або команда wait завершується таймаутом, скористайтеся `kubectl describe pod pod1` і логами CNI ноди перед тестуванням сервісів.
</details>

### Завдання 4: Протестувати зв'язність за IP Под'а, сервісом і DNS

Тепер протестуйте шлях порівнево: спершу прямий IP Под'а, потім Сервіс, потім доступ до сервісу через DNS. Цей порядок важливий, бо збій DNS може приховати цілком справний шлях за IP Под'а, а збій сервісу може приховати справний прямий шлях Под'а. Тримайте тимчасові ресурси малими, щоб очищення було безпечним і швидким.

```bash
# Test pod-to-pod connectivity
POD2_IP=$(kubectl get pod pod2 -o jsonpath='{.status.podIP}')
kubectl exec pod1 -- ping -c 3 "$POD2_IP"

# Create service-backed workload
kubectl create deployment web --image=nginx
kubectl expose deployment web --port=80

# Wait for deployment
kubectl wait --for=condition=available deployment/web --timeout=60s

# Test DNS and service connectivity
kubectl exec pod1 -- wget --spider --timeout=2 http://web
```

<details>
<summary>Настанови до розв'язання</summary>

Якщо зв'язність за IP Под'а працює, але `http://web` дає збій, перевірте, чи має Сервіс ендпойнти, перш ніж звинувачувати CNI. `kubectl get endpointslice -l kubernetes.io/service-name=web` або `kubectl get endpoints web` можуть показати, чи знайшов селектор Под nginx. Якщо ендпойнти існують, переходьте до перевірок kube-proxy та NetworkPolicy.
</details>

### Завдання 5: Перевірити kube-proxy, CoreDNS і граничний випадок мережі хоста

Завершіть перевіркою компонентів, які часто плутають із CNI. kube-proxy володіє маршрутизацією ClusterIP, CoreDNS володіє розрізненням імен сервісів, а Под'ам із мережею хоста потрібна явна політика DNS, коли вони мають використовувати DNS кластера. Приклад мережі хоста також показує, чому обхід звичайної мережі Под'ів має бути навмисним вибором дизайну.

```bash
# Check kube-proxy pods, mode config, and recent proxier logs
kubectl get pods -n kube-system -l k8s-app=kube-proxy
kubectl get configmap kube-proxy -n kube-system -o yaml | grep -A2 '^[[:space:]]*mode:'
kubectl logs -n kube-system -l k8s-app=kube-proxy --tail=20 | grep -iE 'Using|Proxier|mode'

# Check CoreDNS
kubectl get pods -n kube-system -l k8s-app=kube-dns
kubectl logs -n kube-system -l k8s-app=kube-dns --tail=20

# Create hostNetwork pod with cluster DNS behavior
cat << 'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: host-net
spec:
  hostNetwork: true
  dnsPolicy: ClusterFirstWithHostNet
  containers:
  - name: test
    image: busybox:1.36
    command: ["sleep", "3600"]
EOF

kubectl wait --for=condition=ready pod/host-net --timeout=60s
kubectl get pod host-net -o wide
kubectl exec host-net -- nslookup kubernetes
```

<details>
<summary>Настанови до розв'язання</summary>

Под із мережею хоста має показувати мережеву ідентичність ноди, а не звичайну ізольовану адресу Под'а, і все одно має розрізняти сервіс `kubernetes`, бо встановлено `ClusterFirstWithHostNet`. Якщо DNS сервісу дає збій лише для цього Под'а, порівняйте його конфігурацію резолвера з `pod1`. Якщо маршрутизація сервісу дає збій для всіх Под'ів, поверніться до перевірок kube-proxy та ендпойнтів.
</details>

### Завдання 6: Очищення та критерії успіху

Очистьте кожен об'єкт, який ви створили, і підтвердьте, що простір імен повернувся до своєї початкової форми. Очищення — частина вправи, бо мережеві лабораторії часто лишають тестові Под'и й сервіси, які заплутують подальше налагодження. Коли завершите, скористайтеся контрольним списком, щоб переконатися, що ви справді відпрацювали кожну цільову навичку, а не лише запустили команди.

```bash
kubectl delete pod pod1 pod2 host-net --ignore-not-found
kubectl delete deployment web --ignore-not-found
kubectl delete svc web --ignore-not-found
```

Критерії успіху:
- [ ] Можу ідентифікувати встановлений плагін CNI і чи працює він як DaemonSet.
- [ ] Можу читати докази CIDR Под'ів, CIDR сервісів та CIDR Под'ів ноди, не змішуючи їхні ролі.
- [ ] Можу перевірити зв'язність між Под'ами перед тестуванням DNS сервісу.
- [ ] Можу відрізнити симптоми kube-proxy, CoreDNS та CNI за допомогою цілеспрямованих команд.
- [ ] Можу пояснити, чому `hostNetwork: true` змінює володіння портом та вимоги до політики DNS.
