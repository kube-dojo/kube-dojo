AI Engineering Foundations Wave 4 — Stage-0 research brief

Date: 2026-05-25 · Author: orchestrator · Predecessor: docs/research/ai-engineering-foundations-stage0-2026-05-15.html

Recommendation: Create the final 4 modules of the AI Engineering Foundations curriculum (Wave 4), completing the Harness arc and the Symphony capstone. This brief specifies the structural requirements for T0 content authors to produce Bloom L3+ modules covering layers and maps, mechanical guardrails, operational processes, and applied work orchestration.

1. Avoiding duplication (The Orphan Modules)

Wave 4 replaces and heavily expands upon three older, overloaded modules that previously carried the burden of teaching prompts, harness, and orchestration together. Writers must read these legacy modules to understand the learner's baseline vocabulary, but MUST NOT simply restate their contents.

Module 1.6: Prompt Engineering Fundamentals

What it covers: Introduces prompting as an interface contract, separating system/developer instructions from untrusted data, applying few-shot vs zero-shot techniques, and evaluating prompts like engineering artifacts with test cases. It handles basic API structuring, message roles, and prompt schemas.

What NOT to restate: Do not re-teach basic prompt formatting, message hierarchies (system/user), prompt debugging loops, or how to write basic examples. The learner already knows prompts are API boundaries.

How to reframe: Wave 4 (specifically Module 3.2 Guardrails) must reframe safety from "writing defensive prompts" into "building mechanical execution rails and platform-level schemas" that operate completely outside the prompt window.

Module 2.1: Harness Engineering (Legacy)

What it covers: The foundational seven principles of harness engineering by Lopopolo, distinguishing platform defaults from project advisory and enforcement layers. It introduces local branch policies, manifest invariant checks, and trace observability via local hooks.

What NOT to restate: Do not re-teach the high-level justification for the 7 principles, the basic explanation of "map over manual," or simple introductory bash invariant checks. The learner already accepts that harness is necessary.

How to deepen: Wave 4 splits this into three concrete operational modules. 3.1 deepens the system of record and mapping architecture. 3.2 corrects the assumption that simple linting is enough by exploring agent-legible observability, devtools wiring, and complex structural guardrails. 3.3 reframes the harness from a static setup into a continuous lifecycle (doc-gardening, exception drift management, and garbage collection).

Module 2.2: Orchestrating Fleets: Symphony (Legacy)

What it covers: The pivot from session-centric control to ticket-centric project management, detailing the WORKFLOW.md contract, the four lifecycle hooks (after_create, before_run, after_run, before_remove), and the separation of internal claim states from tracker states.

What NOT to restate: The basic argument for why issue-first orchestration is better than session-first, the basic YAML structure of WORKFLOW.md, or the names of the four baseline lifecycle hooks.

How to apply: Module 4.1 must take these structural concepts and apply them operationally. It should deepen how to manage state machine transitions dynamically (e.g., using objective-driven tasks instead of rigid transitions), how to hot-reload configurations safely, and how to build verifiable evidence packages (Proof of Work) for human reviewers when the agent completes its run.

2. Module Specifications

Module 3.1: Harness Fundamentals — Layers and System of Record

Why this module exists: After mastering dynamic context orchestration (Module 2.4), an engineer can manage ephemeral turn state efficiently but still lacks a persistent control plane to govern agent behavior across independent sessions. This module bridges that gap by establishing the repository itself as the system of record. It defines exactly where platform defaults end and project enforcement begins, ensuring every agent starts with a stable, machine-readable map rather than ambiguous ad-hoc instructions.

Learning Outcomes:

  • Design a three-tier harness architecture that correctly classifies rules into platform defaults, project advisory, and project enforcement layers.
  • Evaluate repository structures to separate durable policy (System of Record) from transient session evidence.
  • Implement an agent-facing map (e.g., AGENTS.md) that deterministically routes agents to authoritative policy paths without manual search.
  • Compare instruction-driven compliance with architectural constraint compliance when mitigating recurring agent failures.

Topic Bullets:

  • The limitations of prompt-level instructions for durable policy enforcement across fleets.
  • The three-layer harness model: platform runtime, project advisory docs, and hard project enforcement.
  • The repository as the ultimate System of Record (SoR) for autonomous agents.
  • Structuring maps (e.g., AGENTS.md and CLAUDE.md) as control artifacts, not prose manuals.
  • Progressive disclosure: anchoring specific paths rather than dumping massive context blocks.
  • Reducing semantic ambiguity in the first 30 seconds of an agent task loop.
  • Boring tech bias: prefer static markdown files and simple shell scripts over complex databases for policy control.

Primary References:

  • https://openai.com/index/harness-engineering/ (Lopopolo's core harness post)
  • https://model-spec.openai.com/2025-09-12.html (OpenAI Model Spec for platform layer constraints)

Hands-on exercise: Learners design a mock repository layout defining a 3-tier harness. They create an AGENTS.md map and a set of interconnected policy files, then simulate an agent traversal using basic CLI tools to prove the map resolves ambiguity for a specific deployment failure scenario.

Module 3.2: Guardrails, Gates, and Agent-Legible Apps

Why this module exists: While Module 3.1 builds the map, an agent must still execute actions within an environment that can silently fail or allow dangerous operations. Engineers need to know how to build mechanical boundaries that reject unsafe outputs and expose internal app states clearly. This module shifts focus from advising the model (via prompts) to explicitly hard-gating its execution and providing deterministic error telemetry for autonomous remediation.

Learning Outcomes:

  • Implement structural guardrails (e.g., schema validators, syntax linters) that enforce output contracts strictly outside the prompt window.
  • Design agent-legible observability surfaces that emit deterministic trace state, health metrics, and bounded JSON logs.
  • Diagnose execution loops by treating application errors as actionable remediation signals.
  • Compare the blast radius and reversibility of specific operations to determine which actions require hard blocking gates versus automated retries.

Topic Bullets:

  • The systemic failure of "prompt-only" safety in production agent fleets.
  • Mechanical guardrails vs. semantic guardrails.
  • Output schema validation and structured data enforcement as the primary execution gate.
  • Making applications "agent-legible": emitting structured, predictable state rather than human-readable noise.
  • Designing errors as remediation paths (actionable, deterministic error messages).
  • Devtools wiring: connecting linters, tests, and pre-commit hooks directly to the agent's feedback loop.
  • Least privilege execution, sandboxing principles, and environment variables as boundaries.

Primary References:

  • https://genai.owasp.org/llmrisk/llm01-prompt-injection/ (OWASP LLM01 on untrusted data boundaries)
  • https://docs.anthropic.com/en/docs/build-with-claude/tool-use (Anthropic Tool Use and structured constraints)

Hands-on exercise: Learners build a local invariant bash script that parses an agent's proposed YAML manifest. They configure the script to fail deterministically with a structured remediation message when a required security context block is missing, forcing the agent into a closed-loop repair cycle.

Module 3.3: Operating the Harness

Why this module exists: A static harness configuration degrades rapidly under high-throughput autonomous workloads, resulting in exception drift and stale policies. Engineers need to learn how to operate, maintain, and prune the harness over time. This module teaches the day-two operations of an AI-native workspace, moving from building checks to governing the lifecycle of those checks, managing merge velocity, and continuously garbage-collecting obsolete agent rules.

Learning Outcomes:

  • Diagnose exception drift by identifying temporary workaround policies that have calcified into invisible technical debt.
  • Implement a continuous garbage collection process to prune stale map links, obsolete exception entries, and duplicated hook logic.
  • Design an escalation matrix to route agent failures to human review based on retry limits and cost-of-bad-output.
  • Compare high-velocity merge philosophies, identifying when to automate retries versus when to force human confirmation gates.

Topic Bullets:

  • The operational decay of agent harnesses: instruction debt versus enforcement debt.
  • Exception drift and managing the danger of permanent "temporary" incident workarounds.
  • Continuous garbage collection (GC) of AGENTS.md, stale prompt templates, and old validation scripts.
  • Doc-gardening as a first-class, scheduled engineering maintenance task.
  • Adapting merge philosophy for AI scale: separating deterministic low-risk paths from high-risk manual review paths.
  • Managing human-in-the-loop escalation thresholds.
  • Synchronizing the three operational clocks: policy freshness, enforcement freshness, and recovery freshness.

Primary References:

  • https://openai.com/index/harness-engineering/ (Harness lifecycle and operational maintenance sections)
  • https://linear.app/developers (Linear API documentation as an example of operational issue state modeling)

Hands-on exercise: Learners audit a synthetic repository containing conflicting policies, stale incident exceptions, and broken map targets. They perform a rigorous doc-gardening sweep to prune the obsolete artifacts and update the harness map to a single source of truth without breaking existing integration test scripts.

Module 4.1: Symphony — Work Orchestration as Applied Harness

Why this module exists: Modules 3.1-3.3 secure the repository environment, but do not schedule or track asynchronous agent workloads across a team. This capstone applies the entire harness framework to the project management layer. It teaches engineers how to orchestrate fleets of agents using issue trackers (like Linear or GitHub) as the definitive control plane, ensuring that agent activity translates into verifiable, human-reviewable progress without overwhelming human operators.

Learning Outcomes:

  • Implement an issue-first orchestration loop that delegates control state to a project management tracker instead of a local ephemeral session.
  • Design a dynamic WORKFLOW.md contract that governs workspace cloning, hook execution, and polling behavior via hot-reload.
  • Compare rigid state machine transitions with objective-driven progression to determine the safest automation strategy for a given class of task.
  • Evaluate a "Proof of Work" package generated by an autonomous run to make safe, confident merge and release decisions.

Topic Bullets:

  • The conceptual pivot from terminal-session metrics to ticket-completion metrics.
  • The PM tracker (GitHub Issues/Linear) as the ultimate control plane for fleet orchestration.
  • Practical application of the 4 lifecycle hooks (after_create, before_run, after_run, before_remove) and their specific failure semantics.
  • Building persistent workpad comments to survive attempt retries, preserve context, and prevent timeline spam.
  • Dynamic WORKFLOW.md adjustments: hot-reloading configurations to manage concurrency limits and blast radius during incidents.
  • Transitioning from strict state choreography to objective-driven thresholds (e.g., KubeDojo's /goal paradigm).
  • Assembling "Proof of Work" artifacts (CI results, diff analysis, objective completion checks) for human handoff.

Primary References:

  • https://github.com/openai/symphony/blob/main/SPEC.md (Symphony Specification Document)
  • https://github.com/openai/symphony/blob/main/README.md (Symphony architectural overview)

Hands-on exercise: Learners configure a minimal WORKFLOW.md file and a polling bash script that reads issues from a mock GitHub repository via the CLI. They simulate a failing after_run hook to observe how the orchestrator gracefully preserves the ticket state in a "RetryQueued" mode without losing the persistent workpad evidence.
