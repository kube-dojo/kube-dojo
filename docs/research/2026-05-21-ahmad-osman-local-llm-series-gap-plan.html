Top technical claims compiled from all 3 parts:

  1. Hardware strategy + workload shape first; engine selection follows.
  2. Memory bandwidth is often the primary bottleneck for decode speed, more so than raw VRAM capacity.
  3. KV cache growth is the dominant bottleneck on long context + batched workloads; PagedAttention is the answer.
  4. Interconnect quality and scheduler quality (continuous batching) become critical in multi-GPU production.
  5. Engine decision tree by hardware tier: llama.cpp / MLX-LM / ExLlamaV2 / ExLlamaV3 / vLLM / SGLang / TensorRT-LLM / NVIDIA Dynamo.
  6. Ollama is not for production.
  7. Concrete local tier: 2× used RTX 3090 + Qwen 3.6 27B or Gemma 4 31B can match prosumer-cloud quality.
  8. Prefill phase is compute-bound; decode phase is memory-bandwidth-bound.
  9. Benchmark metrics that matter: TTFT, TPOT, p95/p99 latency, concurrency, cache hit rate.
  10. Acquire compute now — GPU supply / pricing pressure.

2. The teaching critique

User: "i dont liek this articles they are not good teaching materials and we should create good teaching material about these"

Concur. The series is high-density social-media-thread content — strong opinions, strong recommendations, very little explanation. As teaching material it has three problems:

  • Recipe without theory. The decision tree at the end of part 3 is correct, but a learner who memorizes the tree cannot generalize it to a new engine that ships next quarter. The underlying mental model (memory hierarchy → workload shape → engine class) is hinted at but not taught.
  • "Buy GPUs now" framing. The market-timing thesis ages fast and isn't curriculum content. The capacity / bandwidth math behind it IS curriculum, but the urgency framing is signal not knowledge.
  • No verification gates. Claims like "ExLlamaV3 has better multi-GPU and MoE support" are stated as facts with no benchmark, no source, no failure mode. Learners cannot validate them against their own hardware.

4. Proposed new / expanded modules

Module A — "GPU Memory Hierarchy and Bandwidth Math for LLM Inference" recommended T0/T1

Where: src/content/docs/ai-ml-engineering/ai-infrastructure/module-1.6-memory-bandwidth-math.md (new; sidebar order 706, after the local-stack + cost-model modules).

Why: The single biggest curriculum gap exposed by the Osman series. Bandwidth is the dominant decode-phase bottleneck and we have NO standalone module on memory hierarchy + arithmetic-intensity reasoning. Learners currently get bandwidth as a tactical aside inside the vLLM/sglang module.

Learning outcomes (target 4-5):

  • Differentiate the memory layers (HBM2/HBM2e/HBM3, GDDR6/GDDR6X, system DRAM, NVLink/PCIe) by bandwidth, capacity, and cost.
  • Calculate arithmetic intensity for a given (model size × precision × batch × seq-len) configuration and predict whether the workload is compute-bound or memory-bound.
  • Predict decode token-per-second from model weight size and observed bandwidth, then validate against a measured benchmark.
  • Explain why HBM-equipped data-center GPUs (H100, B200, MI300X) win at decode-throughput vs consumer GDDR cards despite similar TFLOPS, and when that gap matters.
  • Use bandwidth math as the first input to engine + hardware selection — before considering specific products.

Sources to seed: NVIDIA H100 / RTX 5090 / RTX 4090 / RTX 3090 spec sheets (HBM3, GDDR6X bandwidth); Apple M2/M3 Ultra unified-memory bandwidth docs; Sébastien Bubeck-style arithmetic-intensity blog posts; vLLM/SGLang docs on PagedAttention and KV cache memory transfer; Tim Dettmers's blog (capacity + bandwidth analyses); Modal Labs benchmark posts.

Module B — "Production-Tier LLM Inference Engines: Decision Framework" recommended T0/T1

Where: src/content/docs/ai-ml-engineering/ai-infrastructure/module-1.7-production-inference-engines.md (new; sidebar order 707, sibling to the learner-stack decision module).

Why: We have a learner-scale decision module (Ollama / llama.cpp / MLX / vLLM) and a vLLM/SGLang deep-dive. We do NOT have a production-tier engine selection module that systematically covers ExLlamaV2/V3 (consumer CUDA), TensorRT-LLM (NVIDIA datacenter), NVIDIA Dynamo (cluster orchestration), and TGI / LMDeploy / OpenVINO as niche options. Without this, the curriculum stops at "use vLLM" and learners hit a cliff when they need NVIDIA-max performance or 2-4 GPU consumer setups.

Learning outcomes:

  • Map each engine (ExLlamaV2, ExLlamaV3, vLLM, SGLang, TensorRT-LLM, NVIDIA Dynamo, TGI, LMDeploy) to its target hardware tier and workload class.
  • Select an engine for a given (GPU count, model family, context length, concurrency, MoE/dense, NVIDIA-only vs portable) profile using a deterministic decision flow.
  • Diagnose the specific failure modes that justify "do not use Ollama for production" (no continuous batching, no concurrency safety, blocking request model, no observability).
  • Plan an upgrade path from a learner-scale runtime (Ollama / llama.cpp) to a production engine without rewriting the application layer.
  • Compare engine maturity by deployment surface (single binary vs Kubernetes operator), observability, and quantization support across at least four engines.

Sources to seed: vLLM docs, SGLang paper + docs, TensorRT-LLM docs + LMSYS benchmark posts, ExLlamaV2/V3 GitHub readmes + turboderp's release notes, NVIDIA Dynamo docs, HuggingFace TGI docs, LMDeploy + MLC LLM project docs, Ahmad Osman series as referenced commentary (NOT primary source).

Module C — "Benchmarking LLM Inference: TTFT, TPOT, and Workload-Aware Load Shaping" optional T1

Where: src/content/docs/ai-ml-engineering/ai-infrastructure/module-1.8-inference-benchmarking.md (new; sidebar order 708) OR a substantial expansion-section inside module 1.3.

Why: Benchmarking is currently a sub-section of the vLLM/SGLang module. Pulling it out gives learners a load-bearing skill (how to measure their stack) that applies regardless of which engine they pick. Strong fit for a hands-on lab.

Learning outcomes:

  • Define TTFT, TPOT, p50/p95/p99 latency, throughput, and prefill/decode token-rate, and explain when each matters.
  • Run a structured benchmark with synthetic workload (variable prompt length, concurrency, prefix-cache reuse) using vLLM's benchmarks/benchmark_serving.py or a parity script for the chosen engine.
  • Interpret benchmark results to diagnose memory-bound vs compute-bound regimes and identify the bottleneck on the production hardware.
  • Tune serving parameters (max-num-seqs, max-num-batched-tokens, gpu-memory-utilization) using the measurements rather than defaults.

Decision: defer Module C? Mark as P2.

If we ship only A + B, that closes the largest gaps the Osman series exposes. Module C is incremental polish on existing 1.3 content. Recommend A + B as priority; C as follow-up if the data-ai discipline gets another sprint.

6. What I would NOT do

  • Don't cite the Osman series as a curriculum source. It's commentary, often unsourced. Use it as a topic-discovery signal only.
  • Don't write a "buy GPUs now" module. Market commentary is not curriculum.
  • Don't reflexively rewrite modules 1.3 / 1.4 / 1.6 — they're already strong on the topics they cover. Add new modules for the gaps; expand only where audit reveals a missing claim.
  • Don't add a separate "Ollama failure modes" module. One Common-Mistakes-table row in Module B is the right size.
