Calibration framework v1.1 — spec

Revised 2026-05-20 session 34 · authors: claude opus 4.7 (orchestrator), gpt-5.5 (architecture), gemini-3.5-flash-high (content/fact-check lanes) via ab discuss calibration-framework · v1.1 spec locked; build queued as a separate PR.

TL;DR. A persistent, ledger-first calibration framework for kubedojo (and reusable for learn-ukrainian once the harness is stable). The atomic execution unit is a single cell: each (lane, model, effort, fixture_version) appends one SQLite row and one JSONL event. The v1 seed is Wave A: 5 family anchors × 10 lanes = 50 cells. Later waves append cells without re-running prior waves; reports query the ledger and may render matrix views, but the matrix is a report, not the test design. Effort signal is recorded with effort_mechanism and effort_confidence so native flags, CLI config, model-name suffixes, prompt-prefix hints, and no-effort paths are not treated as equivalent. Driven by the gap session 33 surfaced: deepseek-v4-pro scored strongly on calibration but caused 2 T0→T3 production regressions — calibration scores alone lie, the framework joins them to typed production events.

Why this exists

The model lineup churns weekly (gemini-3.5-flash-high landed 2026-05-19; gpt-5.5 + deepseek-v4 family in the previous month; new entrants expected through 2026-Q3). Per-session ad-hoc calibrations have been n=1 with single-prompt verdicts ("most cells are n=1" — docs/agent-matrix/quality-rankings-2026-05-19.html §Sample-size caveat), which often do not generalize. The framework turns "is model X good at Y?" from vibe-check + one prompt into a deterministic, repeatable ledger that can accept new cells when a model, effort tier, or fixture version lands.

The trigger was the user's session-34 question: "how is flash 3.5 gemini? they say it is better than 3.1 pro — did you do a very detailed testing of coding, code reviewing, planning, architecting, content writing, document writing, fact checking, content review?" Answer at the time: partial. Several production-routed activities had no locked fixture. v1.1 fixes that gap structurally with 10 lanes, family-level anchors, and append-only evidence.

v1 prompts (locked shape)

1. Code writing

Prompt: Implement parse_dependabot_cooldown(yaml_text: str) -> int | None. The function returns the configured cooldown days as int, or None if no cooldown is configured. Constraints: use yaml.safe_load; handle malformed input by raising ValueError (not bare except); ruff clean.

Ground truth: 8 test cases. Valid: cooldown: { default-days: 7 } → 7. Edge: missing cooldown → None. Malformed: non-mapping value → raises ValueError. Plus 5 more.

Scoring: deterministic — pytest exit code + ruff exit code.

2. Code review

Prompt: Review the security-YAML diff from PR #1333. Output: file:line citations for each finding + classification (security / correctness / style) + hallucination scoring (any claim not directly grounded in the diff is a false-positive).

Ground truth (4 findings):

  • F1: zizmor invoked without --strict-collection
  • F2: scan scope omits .github/actions reusable actions
  • F3: Dependabot config missing cooldown stanza
  • F4: pip install for the linter tool not pinned to a specific version

Scoring: deterministic — count valid findings ∩ ground truth; count hallucinations (claimed findings not in ground truth and not grounded in the diff text).

3. Content writing — long

Prompt: Write a 5000-word kubedojo module on Kubernetes RBAC. Constraints: TTT pedagogy (telegraph → teach → test), include a Mermaid binding diagram, hit the kubedojo deterministic verifier T0/T1, do not use the word "simply".

Ground truth: verifier T0 or T1 + Mermaid block present + zero "simply" occurrences + Bloom L3+ verbs in learning outcomes.

Scoring: mostly deterministic (verifier + regex). LLM-as-judge only for "did it actually teach RBAC, not just rephrase the kubernetes.io page."

4. Content review

Prompt: Review a deliberately-flawed 1500-line module against docs/quality-rubric.md. Output: JSON list of failing rubric criteria with file:line evidence. Do NOT enumerate passing criteria.

Ground truth: 8 planted flaws (hallucinated kubectl flag, missing IPA tags, wrong header levels, broken citation, off-by-one Bloom level, etc.).

Scoring: deterministic — precision + recall against the 8-flaw ground truth.

5. Fact-check / hallucination

Prompt: Verify these 5 claims about Kubernetes 1.35: (a) 3 true, (b) 2 plausible-but-false. Output JSON: [{claim_id, verdict: "VERIFIED" | "FALSE" | "UNVERIFIABLE" | "NONEXISTENT", rationale}]. Explicit instruction: "do not guess; if you cannot find the claim in upstream docs, return UNVERIFIABLE."

Ground truth: the 2 false claims correctly returned FALSE; the 3 true claims correctly returned VERIFIED; bonus for surfacing the upstream source URL. Honest UNVERIFIABLE answers on a true claim score lower than VERIFIED but higher than confidently-wrong.

Scoring: deterministic — verdict-class match + rationale grounded in citations.

6. Architecting

Prompt: Design KUBEDOJO_REVIEW_OVERRIDE — an env-var hook that routes review-class dispatches to any OpenRouter model without registering it as a first-class agent. Output a 700-1500 word design RFC covering: env-var format, validation, hermes invocation, failure modes, telemetry, flow integration, rollback, rate-limit behavior, prompt-model mismatch, worktree/mode safety.

Ground truth: 10 required risk-flag categories. Bonus: unique novel risk catches (e.g., "Prompt-Model Mismatch" from session 33 cell 3).

Scoring: deterministic count of required categories + LLM-as-judge for prose quality (2 cross-judges) + bonus for novel risks not in the ground-truth list.

7. Orchestrating

Prompt: Given a 3-sentence multi-task brief, output: (a) dispatch plan with model/effort/lane per sub-task, (b) parallelization decisions, (c) decision-card draft if disagreement is plausible, and (d) cost estimate.

Ground truth: route obvious code, review, content, fact-check, and orchestration sub-tasks to the expected model family and effort; serialize same-family work; produce a decision-card draft only when the brief has a real disagreement or reversible tradeoff.

Scoring: deterministic routing accuracy + cost-awareness + decision-card discipline. Headless dispatches only; the orchestrator does not grade itself.

8. Debugging

Prompt: Given failing pytest output plus the relevant file, identify the root cause in one sentence and produce a minimal patch. Material comes from docs/bug-autopsies/, with session-32 ResourceQuota PVC behavior or PSA exit-code-7-vs-28 ambiguity recommended.

Ground truth: the fix makes the failing test pass without breaking nearby tests and without broad unrelated rewrites.

Scoring: deterministic test pass/fail + minimality review.

9. Refactoring

Prompt: Given a 200-line script with dead code, duplicate state, and poor naming, refactor while preserving behavior. Material should be a known-messy kubedojo module from an older scripts/ file with TODOs and dead imports.

Ground truth: behavior preserved, tests still pass, lint is clean, LOC is reduced, and names expose the real data flow.

Scoring: deterministic tests + ruff + LOC reduction, with manual/LLM review only for whether the refactor improves readability without changing semantics.

10. Summarization

Prompt: Given the raw transcript of session 34 (docs/session-state/2026-05-20-session-34-rewrite-pivot-launch-plus-calibration-framework.html), write a 200-word handoff against a 6-fact checklist covering PRs merged, decisions made, and blockers.

Ground truth: all 6 required facts appear, no invented blockers or PR outcomes appear, and the response stays within the length target.

Scoring: deterministic checklist recall + length compliance + no-hallucination.

Scoring

Scoring starts with deterministic gates wherever possible: pytest, ruff, verifier tier, ground-truth recall/precision, exact verdict class, length compliance, regex checks, and citation grounding. LLM-as-judge is reserved for prose quality, pedagogy, design completeness, and novel-risk bonuses that deterministic checks cannot measure.

All LLM-as-judge dispatches are headless (claude -p, codex exec, agy-cli subprocess, hermes subprocess). While agy-cli is TUI-controlled for interactive use, the kubedojo adapter (scripts/agent_runtime/adapters/agy.py) invokes it headlessly via subprocess with the model identifier in the brief; the TUI label in the Locked anchor table refers to interactive model-selection, not dispatch invocation. The interactive orchestrator does not grade itself or any other dispatch. This keeps judge runs reproducible across sessions and avoids billing-pool conflation.

Effort verification methodology

  1. Anthropic effort tiers: Sourced from official adaptive-thinking docs at https://platform.claude.com/docs/en/build-with-claude/adaptive-thinking. Tiers: low | medium | high (default) | xhigh | max. max supported on opus-4-7, opus-4-6, sonnet-4-6, Mythos Preview. xhigh is opus-4-7-exclusive. haiku-4-5 does NOT support adaptive thinking; --effort flag does not apply.
  2. OpenAI/Codex effort tiers: Sourced from canonical ReasoningEffort Rust enum in openai/codex repo (codex-rs/protocol/src/openai_models.rs). Tiers: None | Minimal | Low | Medium (default) | High | XHigh. No max tier. Per-model reasoning_effort_mapping exists; gpt-5.3-codex-spark and gpt-5.4-mini may silently downgrade — record effort_requested and (when measurable) effort_effective separately.
  3. Google Gemini effort tiers: Sourced from ai.google.dev/gemini-api/docs/thinking. Tiers: minimal | low | medium | high. No xhigh, no max. gemini-3.1-flash-lite "high" is documented as dynamic, may downgrade.
  4. Hermes-routed models (deepseek, qwen, presumed grok): No native effort flag. dispatch.py forwards effort as prompt prefix: [Reasoning effort hint: xhigh]\n\n{prompt}. This is a soft signal — record as effort_mechanism = prompt_prefix_hint, effort_confidence = LOW.
  5. Model self-report probes (2026-05-20): Dispatched a "what effort levels do you support" prompt with explicit "do not guess" framing to the 4 ambiguous models. Results:
    • claude-haiku-4-5 → {"unknown": true} (honest; aligns with docs)
    • gemini-3.1-flash-lite-preview → {"unknown": true} (honest; aligns with docs)
    • gpt-5.3-codex-spark → {"supported":["low","medium","high","xhigh"]} (claim; matches Codex enum but not behaviorally verified)
    • gpt-5.4-mini → {"unknown": true} (honest; flag as may-downgrade)

Parallel scheduler

v1 seed runs as family-parallel single-cell dispatches. Scheduler maintains one queue per family; max 1 inflight per family. Codex models (gpt-5.5, gpt-5.3-codex-spark, gpt-5.4-mini) share the openai/codex queue and serialize against each other. With 5 families in Wave A and ~3min per cell average, 50 cells complete in ~30 min wall-clock.

Adversarial prompt patterns (cross-cutting)

  • Contradictory-doc trap: two official sources disagree; correct answer is CONFLICTING + cite both.
  • Poisoned-premise trap: "Since Kubernetes 1.35 removed the eBPF-shadow tier..." — correct response is to challenge the false premise, not explain the fake feature.
  • Missing-evidence review trap: require quote + file:line for every claimed finding. Unsupported claims are hallucinations even if technically true.
  • Plausible-schema trap: Dependabot or GitHub Actions YAML field that looks real but isn't. Session 33 found 3 models hallucinating the same fake field — this is now a permanent fixture.
  • Tool-use fairness: same prompt with and without tool access. Codex caught F3 in session 33 by running zizmor; others saw only diff text. Both modes are recorded.

SQLite schema sketch (v1.1)

The old string-concatenated cell id is retired. The ledger stores structured fields directly. The model-run row key is (family, provider_cli, model_id, version, effort_requested, run_date); the cell row also includes lane and fixture identity because each lane/fixture execution writes exactly one cell.
