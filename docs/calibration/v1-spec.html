Calibration framework v1 — spec

Designed 2026-05-20 session 34 · authors: claude opus 4.7 (orchestrator), codex gpt-5.5 (architecture), agy/Gemini 3.5 Flash High (content/fact-check lanes) via ab discuss calibration-framework · v1 spec locked; build queued as a separate PR.

TL;DR. A persistent multi-model calibration framework for kubedojo (and reusable for learn-ukrainian once the harness is stable). Tests each model × effort level × activity lane against locked prompts with deterministic ground-truth gates first, LLM-as-judge second. Canonical storage is JSONL + SQLite; Markdown decision notes and HTML matrices are generated reports, not the database. v1 ships a 25-cell smoke suite (5 lanes × 4 anchors + 1 rotating challenger), with shadow production routing as the long-term replacement for static-matrix calibration. The shape is "anchored evidence ledger + shadow routing," not "big static spreadsheet." Driven by the gap session 33 surfaced: DeepSeek V4 Pro scored 5/5 on calibration but caused 2 T0→T3 production regressions — calibration scores alone lie, the framework joins them to typed production events.

Why this exists

The model lineup churns weekly (agy / Gemini 3.5 Flash landed 2026-05-19; gpt-5.5 + deepseek-v4 family in the previous month; new entrants expected through 2026-Q3). Per-session ad-hoc calibrations have been n=1 with single-prompt verdicts ("most cells are n=1" — docs/agent-matrix/quality-rankings-2026-05-19.html §Sample-size caveat), which often don't generalize. The framework turns "is model X good at Y?" from vibe-check + one prompt into a deterministic, repeatable test that can be re-fired when a new model lands and re-run quarterly to detect regression.

The trigger was the user's session-34 question: "how is flash 3.5 gemini? they say it is better than 3.1 pro — did you do a very detailed testing of coding, code reviewing, planning, architecting, content writing, document writing, fact checking, content review?" Answer at the time: partial. 5 lanes had data (Cells 1-6 from session 33 + this session's production data points); 4 lanes were untested. The framework fixes that gap structurally.

What "anchor" means (terminology clarification)

An anchor is a model we keep in every smoke run to provide a stable reference point. Anchors don't rotate. The 5th slot is the challenger — whichever new model we want to evaluate this round (3.5 Flash today, gpt-5.6 next month, qwen-3.7 after that).

What anchoring gains us: (1) regression detection across time (anchors held constant; if claude-sonnet scores 5/5 today and 3/5 next quarter, that's signal). (2) Calibration ceiling — a challenger that doesn't beat any anchor on any lane doesn't earn a roster slot. (3) Cost frontier — the 4 anchors span price/speed bands (cheap spark ↔ premium gpt-5.5 ↔ fast Flash), letting us position new models inside that frontier rather than rate them in a vacuum.

v1 challenger pick: deepseek-v4-pro

Selected because it has both calibration data and a known production failure — exactly the case the framework is designed to detect.

  • Session 30 calibration: DeepSeek V4 Pro scored 5/5 on the controlled review prompt — top-tier per the calibration-only rubric.
  • Session 33 production reality: DeepSeek V4 Pro had approved 2 modules that have since aged poorly (T0→T3 by verifier). Real production data documented in docs/agent-matrix/quality-rankings-2026-05-19.html §Production track record table.
  • If the framework's production-event join works, the matrix should flag deepseek-v4-pro as "high calibration / low production" — that's the smoke test for the framework itself, not just for deepseek.

v1 prompts (locked — codex + gemini contributed)

Each lane has one v1 prompt. n=1 is acknowledged as a v1 limitation; v2 expands to n≥3 per lane after the harness is proven on v1.

Code review (codex anchored)

Prompt: Review the security-YAML diff from PR #1333. Output: file:line citations for each finding + classification (security / correctness / style) + hallucination scoring (any claim not directly grounded in the diff is a false-positive).

Ground truth (4 findings):

  • F1: zizmor invoked without --strict-collection
  • F2: scan scope omits .github/actions reusable actions
  • F3: Dependabot config missing cooldown stanza
  • F4: pip install for the linter tool not pinned to a specific version

Scoring: deterministic — count valid findings ∩ ground truth; count hallucinations (claimed findings not in ground truth and not grounded in the diff text).

Coding (codex anchored)

Prompt: Implement parse_dependabot_cooldown(yaml_text: str) -> int | None. The function returns the configured cooldown days as int, or None if no cooldown is configured. Constraints: use yaml.safe_load; handle malformed input by raising ValueError (not bare except); ruff clean.

Ground truth: 8 test cases. Valid: cooldown: { default-days: 7 } → 7. Edge: missing cooldown → None. Malformed: non-mapping value → raises ValueError. Plus 5 more.

Scoring: deterministic — pytest exit code + ruff exit code.

Architect (codex anchored)

Prompt: Design KUBEDOJO_REVIEW_OVERRIDE — an env-var hook that routes review-class dispatches to any OpenRouter model without registering it as a first-class agent. Output a 700-1500 word design RFC covering: env-var format, validation, hermes invocation, failure modes, telemetry, flow integration, rollback, rate-limit behavior, prompt-model mismatch, worktree/mode safety.

Ground truth: 10 required risk-flag categories. Bonus: unique novel risk catches (e.g., "Prompt-Model Mismatch" from session 33 cell 3).

Scoring: deterministic count of required categories + LLM-as-judge for prose quality (2 cross-judges) + bonus for novel risks not in the ground-truth list.

Content writing — long (gemini anchored)

Prompt: Write a 5000-word kubedojo module on Kubernetes RBAC. Constraints: TTT pedagogy (telegraph → teach → test), include a Mermaid binding diagram, hit the kubedojo deterministic verifier T0/T1, do not use the word "simply".

Ground truth: verifier T0 or T1 + Mermaid block present + zero "simply" occurrences + Bloom L3+ verbs in learning outcomes.

Scoring: mostly deterministic (verifier + regex). LLM-as-judge only for "did it actually teach RBAC, not just rephrase the kubernetes.io page."

Content review (gemini anchored)

Prompt: Review a deliberately-flawed 1500-line module against docs/quality-rubric.md. Output: JSON list of failing rubric criteria with file:line evidence. Do NOT enumerate passing criteria.

Ground truth: 8 planted flaws (hallucinated kubectl flag, missing IPA tags, wrong header levels, broken citation, off-by-one Bloom level, etc.).

Scoring: deterministic — precision + recall against the 8-flaw ground truth.

Fact checking (gemini anchored)

Prompt: Verify these 5 claims about Kubernetes 1.35: (a) 3 true, (b) 2 plausible-but-false. Output JSON: [{claim_id, verdict: "VERIFIED" | "FALSE" | "UNVERIFIABLE" | "NONEXISTENT", rationale}]. Explicit instruction: "do not guess; if you cannot find the claim in upstream docs, return UNVERIFIABLE."

Ground truth: the 2 false claims correctly returned FALSE; the 3 true claims correctly returned VERIFIED; bonus for surfacing the upstream source URL. Honest UNVERIFIABLE answers on a true claim score lower than VERIFIED but higher than confidently-wrong.

Scoring: deterministic — verdict-class match + rationale grounded in citations.

Adversarial prompt patterns (cross-cutting)

  • Contradictory-doc trap: two official sources disagree; correct answer is CONFLICTING + cite both.
  • Poisoned-premise trap: "Since Kubernetes 1.35 removed the eBPF-shadow tier..." — correct response is to challenge the false premise, not explain the fake feature.
  • Missing-evidence review trap: require quote + file:line for every claimed finding. Unsupported claims are hallucinations even if technically true.
  • Plausible-schema trap: Dependabot or GitHub Actions YAML field that looks real but isn't. Session 33 found 3 models hallucinating the same fake field — this is now a permanent fixture.
  • Tool-use fairness: same prompt with and without tool access. Codex caught F3 in session 33 by running zizmor; others saw only diff text. Both modes are recorded.

SQLite schema sketch (v1)

CREATE TABLE cells (
  cell_id TEXT PRIMARY KEY,           -- <lane>-<fixture-id>-<model>@<effort>-<run-date>
  domain TEXT NOT NULL,               -- 'kubedojo' for v1
  lane TEXT NOT NULL,
  fixture_id TEXT NOT NULL,
  model_id TEXT NOT NULL,
  effort TEXT NOT NULL,               -- 'low' | 'medium' | 'high' | 'xhigh' | 'default'
  run_date TEXT NOT NULL,             -- ISO date
  ledger_version TEXT NOT NULL        -- 'v1'
);

CREATE TABLE dispatches (
  cell_id TEXT NOT NULL,
  task_id TEXT NOT NULL,
  dispatch_ts TEXT NOT NULL,
  response_path TEXT NOT NULL,        -- relative path under calibration/<run>/responses/
  latency_s REAL,
  cost_usd REAL,
  PRIMARY KEY (cell_id, task_id),
  FOREIGN KEY (cell_id) REFERENCES cells (cell_id)
);

CREATE TABLE scores (
  cell_id TEXT NOT NULL,
  gate_name TEXT NOT NULL,            -- 'verifier_tier' | 'ground_truth_count' | 'hallucination_count' | ...
  gate_pass INTEGER NOT NULL,         -- 0 | 1
  score_value REAL,                   -- numeric where meaningful; NULL for binary
  scorer TEXT NOT NULL,               -- 'deterministic' | 'llm-judge:<model>' | 'manual'
  PRIMARY KEY (cell_id, gate_name, scorer),
  FOREIGN KEY (cell_id) REFERENCES cells (cell_id)
);

CREATE TABLE production_events (
  event_id INTEGER PRIMARY KEY AUTOINCREMENT,
  model_id TEXT NOT NULL,
  event_type TEXT NOT NULL,           -- 'approved_stayed_t0' | 'approved_later_t3' | 'real_bug_caught' | ...
  pr_number INTEGER,
  occurred_at TEXT NOT NULL,
  evidence_url TEXT                   -- PR URL, audit log, etc.
);

Decisions resolved this session

QuestionResolution
Full matrix vs smoke first?Smoke first (25 cells), not the 390-cell full matrix. Codex + gemini converged on this independently.
MD-as-database (user's first instinct) vs SQLite/JSONL ledger?SQLite/JSONL canonical; MD + HTML are generated reports. Codex's architectural correction; gemini agreed in round 2.
Effort as separate dimension vs folded into model identity?Folded: model@effort is the atomic row key. Avoids hidden averaging.
Production-vs-calibration join formula?Typed event ledger (approved_stayed_t0 / approved_later_t3 / real_bug_caught / hallucinated_blocker / silent_miss / verifier_failure), NOT a single multiplier. Gemini's first-pass 1/(1+patch_turns) was rejected as too lossy.
Shadow routing scope for v1?Both code-review AND content-review from v1 (user decision). Code-review alone was the conservative option; user chose the broader scope.
First domain?KubeDojo. learn-ukrainian forks the harness once stable (user decision).
Schema scope?Multi-domain from day 1 (domain, lane, fixture_id, etc.). Avoids cross-cutting refactor when learn-ukrainian ports.
v1 challenger model?deepseek-v4-pro (user decision). Has both calibration-strong and production-weak data — directly tests whether the framework catches the gap.
