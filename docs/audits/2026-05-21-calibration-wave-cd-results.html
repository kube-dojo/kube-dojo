Fixture design flaw. The harness-following prompt explicitly lists the four binding KubeDojo rules (feedback_dispatch_codex_for_code_changes and friends), so any model that can pattern-match the rule list back into the response trivially passes the rule_recall gate. The lane needs a harder version where the model is given a rule-violating ask without the rule list — it must surface the rule from its own memory/context. Move toward "you have just been pasted a CLAUDE.md; here is the user ask" with the rules embedded in the CLAUDE.md context, not the immediate prompt.

5. Surprising findings

1. gpt-5.3-codex-spark wins the new MCP-use lane outright (1.00 / 10.00). It is the only model that planned the full 5-step canonical sequence (translate_en_uk → verify_word → check_modern_form → check_russian_shadow → search_sources) AND named SUM / Hrinchenko / ESUM by name. Every other model — including opus, sonnet, gpt-5.5, grok — stopped at 4 steps or omitted at least one source citation. This is a real signal that codex's training on tool-use scaffolding pays off on tool-planning tasks even at the spark tier.
2. qwen3.6 (non-plus) is not viable for production routing. 6 of 12 cells either empty or judged 0 (architecting, orchestrating ×2, content- writing-long ×2, summarization). Det rate 0.33, judge avg 5.0 — both worst-in- class. The qwen3.6-plus variant is fine (0.67 / 7.12), so route to plus, not the base SKU.
3. gpt-5.4-mini is incredibly slow on prose lanes. 1116s on content-review (the worst cell of the entire 168-cell ledger), 623s on content-writing-long, 434s on orchestrating, 395s on architecting. Cost-per-call may be cheap, but the wall-clock cost of routing prose work to mini is prohibitive for an interactive pipeline. Keep mini for fast lanes (mcp-use 89s, summarization 16s, harness-following 43s).
4. gpt-5.3-codex-spark beats claude-opus-4-7 on content-writing-long. Spark hit det 0.80 / judge 9.50, opus hit det 0.80 / judge 9.0 — half a point of judge avg in spark's favor. Surprising because opus is widely considered the prose-quality leader. Possible that the content-writing-long fixture (kubedojo-rbac-module) rewards structured, dense output over flowing prose, which suits spark's training.
5. gemini-3.5-flash-high recovered on the new lanes. In Wave A+B (session 36) gemini-3.5-flash-high collapsed on the 3 prose lanes it ran (judge avg 1.67, one empty response). On the 2 new lanes it landed 0.67 / 8.50 (mcp-use) and 1.00 / 10.00 (harness-following). The model is viable for tool-planning + rule-following despite its collapse on free-form prose. Promotes it back into the supplemental-reviewer pool for non-prose work.

7. Framework improvements landed this session

  • WAL mode by default (scripts/calibration/schema.py:init_db) — eliminates the session-36 lock-contention problem at parallel scoring.
  • agy worktree threading (scripts/calibration/run_cell.py:_effective_cwd) — agy-cli now dispatches from a fresh tempdir, eliminating the 1800s hang that forced session-36 to use sonnet × 2 instead of sonnet + gemini-3.5-flash-high as judges. Confirmed this session: all gemini-3.5-flash-high writer cells completed in <30s.
  • Per-lane judge timeouts (scripts/calibration/score_cell.py:JUDGE_TIMEOUTS_S) — replaced the 1800s judge ceiling with lane-aware budgets (90s for mcp-use/harness-following; 180s for prose lanes). Caught nothing this run, but eliminates the 30-min stall risk on a hanging judge.
  • Parallel judge1 + judge2 dispatch (scripts/calibration/score_cell.py:score_cell) — judges now fan out in 2-thread pool instead of running serially. Saved ~22-44 min on the 88-cell sweep.
  • Pre-flight adapter probe (scripts/calibration/run_wave.py:preflight_probe) — probes one model per distinct (provider_cli, agent_name) pair with a short timeout before opening the full sweep. Already paid off once this session.
  • Lane-set consistency asserts (scripts/calibration/score_cell.py:_assert_lane_set_consistency + run_wave.py:_assert_lane_fixture_consistency) — module-load-time guards that catch "added a lane but forgot to wire SCORERS / LANE_FIXTURES" drift before any cell dispatches.
  • Two new lanes: mcp-use (tool-planning) and harness-following (project-rule adherence). 28 cells run this session across these lanes.
  • Harder fixtures: code-review (k8s-controller-leader-election, 6 planted findings) and debugging (pod-pending-topology-mismatch, EKS multi-AZ scenario). Debugging differentiates; code-review still collapses (scorer issue, not fixture).
  • Committed wave runner (scripts/calibration/run_wave.py) — replaces the ad-hoc session-36 script; family-parallel dispatch + in-line scoring + pre-flight + JSONL summary. --smoke for cheap pipeline validation.

8. Recommendations for next wave

  1. Fix the CodeReviewScorer — replace AND-of-binary-gates with per-finding recall ratio + hallucination-rate ratio. Otherwise the harder fixture also collapses to 0.50-tied.
  2. Rebuild the harness-following fixture — embed the rules in a simulated CLAUDE.md context, not the immediate prompt. The current lane is "can the model echo a rule list" rather than "does the model recognize a rule violation."
  3. Tighten mcp-use gate threshold from ≥0.6 to ≥0.75 on parameter_grounding, OR expand required signals so the 0.67 plateau breaks open.
  4. Route qwen3.6 off all production paths. The base SKU is not viable. Cascade to qwen3.6-plus only.
  5. Add gpt-5.3-codex-spark to the mcp-use reviewer cascade. Wave C/D data shows it is the unique perfect-score model on tool-planning. Should also be tested on shadow code-review duty given its overall det rate (0.77) beats opus (0.74).
  6. Defer routing prose work to gpt-5.4-mini despite its strong score per cell — wall-clock is prohibitive (1116s × 2 on the same model would dominate any pipeline).
