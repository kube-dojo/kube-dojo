Session 166 — Headroom CPU hog + the restart lesson

2026-06-18 · standalone orchestrator · continues s165 (same calendar session, Headroom workstream). TLDR: user reported the Mac was being eaten by CPU. Root cause = the Headroom proxy's --memory mode running the Kompress compression model on CPU via PyTorch instead of the Neural Engine via ONNX/CoreML (80–264% / load 18 over 18h). agy (Gemini) found + fixed the real 2-line bug. The hard lesson: every headroom install restart/start/apply regenerates the launcher + manifest from defaults, wiping the fix and reverting --memory — so my "restart to verify" repeatedly undid agy's fix (the exact thing the user was frustrated about). No KubeDojo PRs this episode; it was infra firefighting.

What was eating the CPU

Top process: python -m headroom.cli proxy ... --memory --memory-db-path ~/.headroom/memory.db at 80–264% CPU, 18h uptime, dragging syspolicyd (164%) + trustd (53%) via its outbound API traffic. Load average 18 on a 10-core box and climbing. The --memory subsystem runs vector/graph embedding work on every request; the model was on CPU.

agy's fix (verified correct + working)

agy found a real bug in headroom/transforms/kompress_compressor.py (v0.26.0, the latest):

-  is_onnx = backend == "onnx"          # lines 785 + 1048
+  is_onnx = backend.startswith("onnx")

The selector only took the ONNX path when backend was exactly "onnx", so "onnx_coreml"/"onnx_cpu" fell back to PyTorch-on-CPU. The fix makes all ONNX variants take the accelerated path. agy also set HEADROOM_KOMPRESS_BACKEND=onnx_coreml in the launcher. Verified: logs show CoreMLExecutionProvider ... 137 nodes supported by CoreML; CPU dropped 264% → ~0% idle; load 18 → ~4. Credit agy — it found the root cause; I was treating the symptom (turn memory off).

⚠ THE LESSON — do NOT restart Headroom to apply config tweaks

headroom install restart / start / apply REGENERATE ~/.headroom/deploy/default/run-headroom.sh AND manifest.json from CLI flags/defaults on every run. They wipe any hand-edit (agy's HEADROOM_KOMPRESS_BACKEND export, a manifest base_env addition) and revert --memory to off. So file-patching the launcher canNOT survive a Headroom restart, and "restart to verify a config edit" is the exact move that keeps undoing agy's fix.
  • The macOS launchctl path is also flaky here: kickstart -k → exit 37 when the service is unloaded; bootstrap → exit 5 when it's still loaded (KeepAlive resurrects it). headroom install start on a running service is the only reliably-working verb seen.
  • My durability attempt (self-heal guard in run-headroom.sh + env var in manifest base_env) was written to disk, then a single install restart regenerated both files and dropped --memory — net effect: I reproduced the breakage the user complained about.
  • Rule for next session: do not run headroom install restart/start/apply to apply a tweak. The proxy self-restarts via launchd KeepAlive; let it. The durable fix is upstream (below), not file edits + restart.
