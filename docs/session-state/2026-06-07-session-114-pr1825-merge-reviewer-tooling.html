2. Why reviewers misbehave + tool-access tooling (#1827)

User asked why the reviewers threw false positives and whether we have trusted reviewers. Root cause: model reviewers run sandboxed from fact-check tools (no web, no gh api, no MCP) so they pattern-match from training → confident FPs on external-state & post-cutoff claims. No model reviewer is merge-on-faith trustworthy; the deterministic tools (verify_module.py, gh api, WebFetch, incident-dedup) + orchestrator ground-check are the trusted layer.

Two restrictions were conflated: write-blocking (deliberate, correct — keep) vs no read tools (the gap). Built/landed:

  • #1828: --mcp SERVER for dispatch_smart review/search classes (scoped to the named server, writes blocked). codex R1 caught a real footgun — claude edit --mcp restricted allowedTools to RAG+Read = silently crippled write → restricted --mcp to read classes.
  • #1830: reviewer-skill rule — when sandboxed, mark live-SHA/post-cutoff/maturity/version claims UNVERIFIABLE, never assert real/fake.

Opus-review economics (saved to memory)

Three wallets: claude -p = capped programmatic pool (post-2026-06-15); Agent-tool subagent = main quota (avoids the pool but token-heavy + competes with the orchestrator); non-Claude = neither. Rule: default reviews on flat-rate non-Claude subs; Opus only for the 1–2 hardest/wave, via subagent not -p, front-loaded at session start; hand off "Opus review pending" rather than cram a depleted session.
