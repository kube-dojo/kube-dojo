Verifier-blind P1s caught by cross-family review (one per module — all fixed + ground-checked)

  • 7.1 — ephemeral OS disk won't deploy on Dsv5 SKUs. The flagship Bicep lab used Standard_D2s_v5/D4s_v5 with osDiskType: Ephemeral, but Dsv5 SKUs have no temp disk so an ephemeral OS must fit the small cache disk (64 GiB > ~50 GiB cache → ARM validation failure). Web-verified Dsv5-no-temp vs Ddsv5-has-temp → switched to D2ds_v5/D4ds_v5. Also removed an invalid az aks create --mode System (the create command's first pool is always System; --mode is a nodepool add/update flag) and simplified a Cilium-without-overlay networkProfile (Cilium data plane requires networkPluginMode: overlay or a pod subnet; CNI selection is deferred to 7.2).
  • 7.2 — fabricated dated/$ opener + a CNI flag contradiction. The "Why This Module Matters" opener was a fabricated real-incident ("In early 2023, a massive European e-commerce organization… $350,000 lost") → relabeled Hypothetical scenario:. A snippet titled "Azure CNI with dynamic IP allocation" wrongly included --network-plugin-mode overlay (overlay gives pods overlay IPs and ignores --pod-subnet-id — the two contradict) → removed; 4 legitimately-labeled overlay snippets left intact. Removed a non-existent az apim create --virtual-network-type flag (--virtual-network Internal already sets the mode).
  • 7.3 — workload-identity label on the wrong object (breaks every lab). azure.workload.identity/use: "true" was on the ServiceAccount but missing from the pod templates — the webhook's objectSelector matches the label on the pod, so no pods get mutated (no AZURE_CLIENT_ID, no projected token; CSI mount + DefaultAzureCredential fail). The module's own Common-Mistakes and Quiz Q6 even said the label belongs on the pod spec — the examples contradicted the prose. opus web-verified the webhook behavior. Moved the label to all 3 pod templates, kept the client-id annotation on the SA. Also fixed misattributed Azure error codes (AADSTS70021 for subject mismatch, not 7000216/700024) and removed a fabricated --service-account-token-lifetime webhook flag (real mechanism is the SA annotation azure.workload.identity/service-account-token-expiration).
  • 7.4 — two non-existent CLI commands break the graded lab. The KEDA lab's core loop used az servicebus queue message send and … purge — neither exists (az servicebus queue has no message subgroup; Service Bus data-plane ops aren't in the CLI). Replaced with an in-cluster SDK/REST producer (workload-identity-authenticated) + a real drain step. Removed an invented KEDA scalingModifiers.strategy: max/min/average field (real schema is formula/target; multiple triggers already take the max by default). Fixed az monitor log-analytics workspace create flags (--retention-time/--quota, not --retention-in-days/--quota-gb), contradictory Ultra-disk IOPS (diagram/matrix said 160,000 vs correct 400,000), PromQL-in-metric-alert, a kubectl-applied-PrometheusRuleGroup mis-framing, the opt-in nature of Managed-Prometheus pod-annotation scraping, and a 404 VPA install URL (+ noted the AKS --enable-vpa add-on). Opener relabeled hypothetical.
  • 7.5 — az fleet updatestrategy --stages needs a file path, not inline JSON. The body example passed inline JSON strings to --stages, which is typed as a path to a {"stages":[…]} file — and the lab section did it correctly, so the body was both broken and self-contradictory. Rewrote to mirror the lab (heredoc → file → path). Added a lab teardown step (the lab spins up 2 AKS clusters + a Fleet hub and never deleted them — a cost-safety gap).
