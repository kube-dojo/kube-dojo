All 5 models failed routing_accuracy despite opus's response visibly making all 4 correct routing calls (codex/gpt-5.3-codex-spark for code-writing, sonnet-4-6 for cross-family code review, codex spark for content draft, gemini-3.1-pro-preview for fact-check) and citing the relevant memory entries by name (feedback_never_flash_for_code_review, feedback_codex_danger_for_git_gh, feedback_html_over_markdown_for_artifacts, etc.).

Root cause in scripts/calibration/score_cell.py:268-285 (OrchestratingScorer):

route_hits = [
    route
    for route in routes
    if _contains_all(response, [route["subtask"], route["model_class"], route["lane"]])
]
return {
    "routing_accuracy": len(route_hits) == len(routes),
    ...
    "same_family_serialized": _contains_any(response, ["serialize", "same-family"]),
}

The gate demands literal AND-of-substring across every subtask — but the ground truth uses author shorthand like "Python bug" while models naturally rephrase to "Bug fix in scripts/check_links.py". The keyword set for same_family_serialized only accepts serialize or same-family; misses queue, sequential, in-order, OpenAI is one lane. opus + gemini happened to use the literal word "serialize"; gpt-5.5/deepseek/qwen used equivalent phrasings and failed.

Compounding: score_cell.py:536-543 implements the spec's 2-stage rule (any deterministic gate fail → cell score = 0, skip LLM-judge). Combined with brittle string-matching, this lost all LLM-judge signal even though opus's prose was clearly high-quality. The 2-stage rule was correctly specced — but assumes the deterministic gates are reliable, which the orchestration scorer is not.

Architectural insight: deterministic gates work well for lanes where there's a single canonical answer (pytest exit code, URL HEAD status, JSON schema validation). They are inherently noisy for prose lanes (orchestrating, refactoring, summarization, content-writing-long, architecting) where the same correct outcome can be expressed many ways. For prose lanes, deterministic gates should not gate the LLM judge. Either the gates should be advisory (recorded but not stop-conditions), or the LLM judge should always run with the gate results as input rather than a precondition.

5 pilot cells remain uncommitted in worktrees/calibration-pilot-orchestrating/ — keep them; next session re-scores after the scorer fix lands (no need to re-dispatch the models, the raw responses are stored and re-scoring is free).
