Part 1 — Mermaid render bug (user-reported, root-caused; two distinct causes)

User: "on some pages the mermaid flows are not rendered, ie: module-4.2-defense-in-depth." Mermaid renders client-side (src/scripts/mermaid-renderer.ts → mermaid.render), so the astro build + site-health are blind to diagram syntax. Found two independent bugs:

  1. Vite stale optimized-deps cache (dev-only) — every diagram on the page failed with Failed to fetch dynamically imported module: …/flowDiagram-*.js?v=…. services.sh stop dev does rm -rf node_modules/.vite; a browser tab left open on the old ?v= hash then requests chunk files the restarted server no longer has. Not a content/prod bug (dist/_astro/ bundles these with stable hashes). This is what produced the "some pages" symptom. Fix = restart dev; recurrence = hard-reload tabs after any dev restart.
  2. Unquoted ( in flowchart node labels (content; affects production) — [Web Server\n(serves static files)] makes the parser read ( as a round-node shape and abort the whole diagram (Parse error … got 'PS'). On the live site these render as raw code (the renderer's error state un-hides the <pre>). Quoted the two 4.2 labels → 8/8 render (verified live in Chrome).

Comprehensive parser audit — the real blast radius

Since the regex lint only knows one pattern, ran a one-time audit: extracted all 2005 mermaid blocks, exposed mermaid.parse via a temporary dev-only hook, validated every block with the real parser. Result: 55 broken diagrams across ~50 files in ~18 distinct error classes — not just parens: PIPE (parens/pipes in edge labels), STR (embedded quotes in unquoted labels), NUM (spaces in node IDs), round-node nested parens (H(Drains (moves))), quadrant/sequence/xychart syntax, even a mojibake stroke: ﬂ°ccc¶ß. This is heterogeneous and needs per-diagram judgment — not a mechanical sweep. User decision: ship only 4.2 + the lint tool now (#1824); the full campaign is a dedicated session (#1823). The temp parse hook was reverted; the 13-file paren-only fix was reverted (reproducible — approach recorded on #1823).
